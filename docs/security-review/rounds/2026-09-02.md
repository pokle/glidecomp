### Executive summary

**One new finding, fixed inline: SEC-48**, a dependency-posture regression
that `bun audit` had gone undetected for at least one full round (11
vulnerabilities, 6 high, up from the 3 dev-time `astro` advisories every
round since 2026-07-26 has carried and reported clean). Root cause: the
2026-08-23 weekly dependency upgrade bumped the `shadcn` CLI tool (a
devDependency confirmed unused — no `components.json`, no script or CI step
invokes it, the RAC migration that made it obsolete finished 2026-07-27 per
CLAUDE.md) from `4.16.2` to `4.19.0`, which re-resolved its transitive `qs`,
`fast-uri` and `browserslist` past what the existing root `overrides` block
actually constrains — the `fast-uri` override in particular reads `^3.1.4`,
which is satisfied by the vulnerable `3.1.5` (the advisory's fixed range
starts at `3.1.6`). None of these are runtime-shipped (all three are
`shadcn`-only or, for `browserslist`, also pulled by the real but
build-time-only `@vitejs/plugin-react`), so exploitability against a live
user is essentially nil — but "dev-time and currently unreachable" is
exactly SEC-34's classification too, and an 11-vulnerability residual four
times the size of the one already being tracked is not something to wave
through undocumented, especially since the dependency-upgrade log's own
audit check that cycle reported no change. **Fixed by bumping/adding three
root `package.json` overrides** (`fast-uri` `^3.1.4` → `^3.1.6`,
`browserslist` added at `^4.28.7`, `qs` added at `^6.15.4`) and re-running
`bun install`; `bun audit` is back to exactly the pre-existing 3 `astro`
advisories, `bun run typecheck:all` and `bun run test:all` are green
(engine/frontend/auth-api/competition-api all pass, counts unchanged from
before the override bump). No source file changed — this is a dependency-
resolution-only fix, so no `scoring-changes/` note applies.

The window's two largest surfaces both got a full read rather than a
diff-skim, given their size. First, the field-analysis → comp/task-analysis
rename (issue #676) and the new per-section contents-list page structure
(issue #675) touch ~55 worker/engine files and a comparable frontend
surface; nearly all of it is confirmed via `git diff -M` rename detection to
be a mechanical identifier rename with the SSR routing, visibility check
(`canViewAnalysis`, unchanged from `canViewFieldAnalysis`) and admin-gating
untouched. Second, the anonymous report-card deep link into the analysis
page (issue #666/#667) is new, security-sensitive surface — an anonymous
visitor can now open `/analysis` at all — and was read end-to-end:
`isPublicCompLink()` is a narrow whitelist (not a blocklist) of exactly the
one param shape the report card emits, every other load path (personal
library, bundled samples, share target) still redirects to sign-in, a
hidden `test` comp still 404s on all four routes the deep link reads with
nothing named in the process, and the sample-loading UI controls that would
otherwise bounce an anonymous reader off the page are hidden via a
`data-requires-account` attribute rather than left live. This matches the
CLAUDE.md rule for this feature exactly, which itself was authored in this
same window — the two are consistent because they landed together.

Third, `validators.ts`'s new `nameText`/`plainText`/`proseText` refinements
(issue #232) are solid, correctly-scoped SEC-22 defence-in-depth: control
characters rejected everywhere, angle brackets rejected on name-type fields
only (with the comment explicitly noting quotes/ampersands stay legal —
`O'Brien`, `"Fly & Co"`), NFC normalisation for canonical-equivalence
dedup/matching, and the code is explicit that none of this replaces output
encoding as the actual XSS boundary. That last point is what makes
**SEC-49** worth documenting rather than fixing urgently: the new
`POST /api/auth/set-name` route (and the pre-existing `set-username`) write
directly to `"user".name` — which is read back as `actor_name` in the
public, per-comp audit log (`ActivitySection.tsx:119/168`, rendered as
plain JSX text, auto-escaped) — with only a 1–128-character length check,
none of the new control-char/angle-bracket/NFC treatment. The route is
directly reachable by any authenticated browser (`functions/api/auth/[[path]].ts`
proxies `/api/auth/*` straight to the auth-api worker; nothing forces a
caller through competition-api's already-validated `newName`), so an
account holder COULD set their display name to include a raw control
character. It is genuinely Info-grade, not exploitable: the two places that
read the account name (`ActivitySection.tsx`'s audit-log rows and the
account-menu/static-chrome consumers) render it as escaped text, exactly
the output-encoding boundary the rest of this defence-in-depth pass relies
on rather than replaces — but it is an inconsistency in an otherwise
comprehensive pass and an easy follow-up (route the two auth-api name
writes through the same `nameText()`-shaped check, or export it from a
package auth-api can import). SEC-05's `html-sinks.test.ts` pin, `bun
audit` composition, and every other prior finding this round's spot-checks
touched are unchanged from the 2026-08-20 round.

- **Files:** `package.json` (root `overrides`), `bun.lock`.
- **Evidence:** `bun audit` on `9bc5d1d..2c34721`'s HEAD reported 11

  GHSA-jqff-g426-hqxp — via `shadcn`; the root override `fast-uri: ^3.1.4`

  `browserslist@4.28.4` (high ×2, GHSA-c83g-rgw3-j3cx,
  GHSA-73wf-gq98-2v4g — via both `shadcn` and the real `@vitejs/plugin-react`
  dependency), plus the pre-existing 3 `astro` advisories. `shadcn` itself
  was bumped `4.16.2` → `4.19.0` by the 2026-08-23 weekly dependency
  upgrade (`7679e08`); confirmed unused in the tree (`grep` for
  `components.json` and any script/CI invocation of `shadcn` both come back
  empty — the RAC migration that made it obsolete finished 2026-07-27).
- **Impact:** Low in practice — all three packages are dev/build-time only
  (`shadcn` CLI tooling nothing invokes; `browserslist`'s `@vitejs/plugin-react`
  path is a Vite build-time dependency, never shipped to the browser or the
  Workers runtime) — but `fast-uri`'s advisories are SSRF-class and
  `browserslist`'s are memory-exhaustion/prototype-write, and an
  11-vulnerability residual silently growing past what the dependency log
  claimed is itself the finding: the log's own audit check is the backstop
  this round's `bun audit` step exists to catch when it's wrong.
- **Remediation (applied):** `package.json` overrides — `fast-uri`
  `^3.1.4` → `^3.1.6` (the advisories' fixed floor), added `browserslist:
  ^4.28.7` and `qs: ^6.15.4`. `bun install` re-resolved; `bun audit`
  confirmed back to exactly the pre-existing 3 `astro` advisories.
  `bun run typecheck:all` and `bun run test:all` both green afterward,
  counts unchanged. No override was loosened or removed — only tightened.

**SEC-49 — Account display-name write (`/api/auth/set-name`,
`/api/auth/set-username`) skips the SEC-22 defence-in-depth applied to
every other user-entered text field this round (Info).**

- **Files:** `web/workers/auth-api/src/index.ts` (`set-name` ~line 199,
  `set-username` nearby), `web/frontend/src/react/comp/ActivitySection.tsx:119,168`.
- **Evidence:** `validators.ts`'s new `nameText()` (control-char rejection,
  angle-bracket rejection, NFC normalisation) is applied to every
  comp/pilot/task name field in competition-api, explicitly as SEC-22
  defence-in-depth. The new `POST /api/auth/set-name` (and the pre-existing
  `set-username`) validate only `1 ≤ length ≤ 128`, written straight to
  `"user".name` via a parameterised `UPDATE`. That column is read back as
  `actor_name` in the public per-comp audit log and rendered as JSX text
  (`<strong>{entry.actor_name}</strong>`, auto-escaped — not a sink) — so no
  XSS follows — but it means a control character or an angle bracket
  reaches the one column the rest of this round's pass just spent effort
  keeping clean everywhere else.
  `functions/api/auth/[[path]].ts` proxies `/api/auth/*` directly to the
  auth-api worker (`context.env.AUTH_API.fetch(context.request)`), so
  `set-name` is reachable directly by any authenticated browser — a caller
  is not required to go through competition-api's already-`nameText()`-
  validated `newName`.
- **Impact:** None currently demonstrable — output encoding at both known
  read sites (JSX text, unaffected by control chars/angle brackets) is the
  actual boundary, exactly as `validators.ts`'s own comment states this
  class of check is not. Purely a defence-in-depth/consistency gap.
- **Remediation (for a future round):** either export the `nameText()`
  refinement (or an equivalent standalone function) from a place auth-api
  can import, or duplicate its two checks inline in
  `web/workers/auth-api/src/index.ts` for `set-name` and `set-username`.
  Small and low-risk, but out of scope for this round per the Medium/Low/
  Info deferral rule — not fixed inline.
