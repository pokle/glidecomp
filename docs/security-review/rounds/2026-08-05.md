### Executive summary

**Two new Medium findings, two new Low findings, none fixed inline (all correctly fall under the Medium/Low deferral rule) — no Critical or High.** The window's headline surface, anonymous track submission (#535), is built with the same discipline this codebase's other deliberately-permissive features use: the trade-off is stated in writing (`docs/track-submission.md`), contained by an explicit organiser opt-in, an unconditional notification email as the detection channel, an audit trail, and per-registration/per-competition rate limiting — and the shared upload-validation code (SEC-11's gzip-bomb cap, SEC-04's size cap) is reused rather than re-implemented, so the new public entry point inherits rather than dilutes those protections. Two gaps surfaced in the parts of this surface that *aren't* the documented trade-off: **SEC-37** (Medium) is that the new `POST /api/comp/:comp_id/registration/resolve` endpoint — unlike every comparable authenticated route in this window — never checks `comp.test`, so a signed-in user who knows or guesses a hidden test competition's id can read its name, its unclaimed roster (pilot names, classes, masked emails) and whether registration is open; the project's own new documentation flags a narrower version of this same class of gap ("only the anonymous route hides test competitions") without having noticed it also applies here. **SEC-38** (Low) is the narrower case the doc did name: the two signed-in IGC-upload POST routes also don't check `comp.test`, so a signed-in user can write a track into a hidden test competition's task, though — unlike SEC-37 — nothing is disclosed by doing so. **SEC-39** (Medium) is that the anonymous route's own anti-abuse budgets are charged in the wrong order: the per-competition (300/day) and per-pilot (6/day) rate limits are charged *before* the competition/task are confirmed to exist and before the named identifier is checked against the roster, so an attacker who knows a real, public competition id can exhaust that competition's entire daily anonymous-submission allowance with garbage requests, 429-ing every legitimate landing-day pilot for the rest of the day — the rate limiter is itself the cheapest lever for the abuse it exists to prevent. **SEC-40** (Low) is a new instance of exactly the algorithmic-complexity class SEC-32/33 just fixed, in code that didn't exist yet when that sweep ran: the new reconstructed-thermals feature's `findSubCores()` clusters samples with an unbounded O(k²) all-pairs loop, mitigated by the pre-existing 80-track field-analysis cap and lazy background scheduling but with zero adversarial test coverage of its own. Separately, **SEC-32 and SEC-33 are confirmed genuinely fixed this round** — not merely landed: the fix mechanism (an incremental order-statistic structure and a monotone deque, replacing two quadratic scans) was read in full, checked for output-parity against the original algorithm via oracle tests, and exercised against the exact adversarial scenarios the original findings specified, all under hard timeouts, with the engine's own version-and-fingerprint discipline (`SCORING_ENGINE_VERSION` 29→30) correctly bumped and changelogged. `bun audit`'s installed-state vulnerability count had drifted up to 16 (from the prior round's 5) — partly because of a genuinely dead dependency (`@base-ui/react`, unused since the RAC migration completed but never removed from the manifest) and partly because a genuinely new, production-relevant advisory appeared against `hono`'s CORS middleware (a ReDoS reachable on every cross-origin preflight to `auth-api` or `competition-api`). A sibling package, `shadcn`, looked equally dead by the same import grep but wasn't — it still supplies the app's base Tailwind token CSS via `globals.css`'s `@import "shadcn/tailwind.css"` — and removing it broke both the e2e webServer and the Pages `Deploy` build; both were caught by this PR's own CI within minutes of opening it, and the removal was reverted before merge (see "Fixed inline" for the full account, offered in the open rather than edited away, per this project's transparency rule). The genuinely dead dependency was removed and `hono` bumped to `4.13.0`, bringing the count to 10, all of it the same class of dev/build-time-only tooling (`astro`, `sharp`, `react-router` RSC-mode, and `undici` via `shadcn`/`wrangler`) the prior rounds have been carrying as SEC-34. `bun run typecheck:all` and `bun run test:all` are green throughout (1339 + 622 + 657 + 97 tests). Elsewhere: site search's new FTS5 index correctly excludes hidden `test` comps at query time despite storing no visibility flag on the indexed documents themselves; the frontend sweep of all ~120 changed files found zero new DOM-sink or CSV-injection issues, and confirmed the new anonymous `/submit` page reuses rather than forks the existing submit-track component (so its transparency guarantees travel automatically); and IGC Forge, despite sounding like a new privileged capability, turns out to have no server-side surface at all — it is a client-only synthetic-file generator whose output must still pass through the same, previously-audited upload pipeline as any real pilot's track.

### New findings

#### SEC-37 — `registration.ts` missing `test`-comp visibility gate — **Medium** — ~~Open~~ **Fixed (2026-08-06, follow-up PR)**

- **Files:** `web/workers/competition-api/src/routes/registration.ts:84-88`.
- **Evidence:** `POST /api/comp/:comp_id/registration/resolve` (auth: `requireAuth` only, no admin check) fetches the competition with:
  ```ts
  const comp = await db
    .prepare("SELECT comp_id, name, open_registration FROM comp WHERE comp_id = ?")
    .bind(compId).first(...);
  if (!comp) return c.json({ error: "Competition not found" }, 404);
  ```
  and never reads or checks `comp.test`. Every comparable authenticated route touched or reviewed this window does check it — `igc.ts:815-822` and `igc.ts:914-921` both run `if (comp.test) { if (!user || !isCompAdmin(...)) return 404 }`; `open-comps.ts` filters `c.test = 0` in its `WHERE` clause; `search.ts` applies `visibleCompsFilter()`. `registration.ts` is the one new endpoint in this window that skips the check entirely, and the class it's returning is not inert: if the competition has any unclaimed roster row, the response includes `registered_pilot_name`, `pilot_class` and a masked email (`notify_email_masked`) for every unclaimed entry (`findUnclaimedRegistrations`, uncapped), plus `open_registration`'s value and the fact that the competition exists at all.
- **Impact:** any signed-in GlideComp user (not just an attacker with special access — any account will do) who knows or guesses a hidden `test` competition's sqid can learn that competition's name, whether it accepts self-registration, and the names/classes/masked-emails of its unclaimed roster. `test` competitions are the organiser's own pre-publish staging area and the project's synthetic-fixture mechanism (`docs/sample-data.md`); either way this is roster data the `test` flag exists specifically to keep non-admins from seeing. Rated Medium rather than High because it requires an authenticated account (not literally public) and a specific comp id (not discoverable via search/lookup, both of which correctly exclude `test` comps), and discloses PII rather than granting a write or an account takeover.
- **Remediation:** add the same gate the file's sibling routes use — select `test` alongside the existing columns, and when `comp.test` is set, require `isCompAdmin(db, compId, user)` or answer `404` exactly as a missing comp would (matching the "a hidden test comp answers exactly as a missing one" convention `igc-anon.ts` and `lookup.ts` already establish). A regression test should assert `state`/`candidates` are never returned for a `test` comp to a non-admin.
- **Resolution (follow-up PR):** the rule is now ONE function — `hiddenFromCaller()` in `comp-visibility.ts`, beside the `visibleCompsFilter()` that answers the same question for a search rather than for a given id, precisely so the next route to be handed a comp id inherits it instead of re-deriving it. `registration/resolve` selects `test` and answers `404 Competition not found` — its own missing-comp wording, not a 403, which would still concede the comp exists — for any caller who is not `isCompAdmin` (super admins included, unchanged). Three regression tests in `test/registration-resolve.test.ts`: a non-admin gets 404 with no `state`, no `candidates` and no roster name anywhere in the body; the comp's own admin still gets `choose`; a super admin still gets `choose` for a comp they do not own.

#### SEC-38 — Signed-in IGC-upload routes missing `test`-comp visibility gate — **Low** — ~~Open~~ **Fixed (2026-08-06, follow-up PR)**

- **Files:** `web/workers/competition-api/src/routes/igc.ts:288-297` (self upload, `POST /api/comp/:comp_id/task/:task_id/igc`) and `:589-601` (on-behalf upload, `POST …/igc/:comp_pilot_id`).
- **Evidence:** both routes select `comp_id, name, close_date, …` (plus `open_registration` or `open_igc_upload` respectively) but not `test`, and neither checks it before proceeding to the close-date/task/authorisation checks. The file's own **GET** routes two hundred lines below (`:815-822`, `:914-921`) do check it. `docs/track-submission.md` (new this window) names exactly this gap in its "Four things that surprise people" section: *"Only the anonymous route hides `test` competitions. Neither signed-in route reads `comp.test`… That is an inconsistency rather than a decision."*
- **Impact:** a signed-in user who already knows a hidden test competition's id and a task id within it (and, for the on-behalf route, is either a comp admin or a registered pilot with `open_igc_upload` on) can upload a track into it. No data is disclosed by doing so (unlike SEC-37) — the impact is limited to writing an unwanted file/roster entry into a competition already excluded from every discovery surface (search, lookup, listing). Rated Low: the comp's own `test` isolation means this can't affect a real competition's scores, and reaching it at all requires already knowing two specific ids a hidden comp's `test` flag is meant to keep obscure in the first place.
- **Remediation:** same fix shape as SEC-37 — select `test`, gate on `isCompAdmin` when set, mirroring the file's own GET-route pattern two hundred lines away. Both SEC-37 and SEC-38 are one-line-per-route fixes against an established in-file pattern; a fast follow-up rather than a full next-round wait would be reasonable given how mechanical the fix is, but per this round's Medium/Low deferral rule neither was fixed inline.
- **Resolution (follow-up PR):** both POST routes select `test` and call the same `hiddenFromCaller()` gate SEC-37 uses, immediately after the comp lookup — ahead of the close-date check, the task lookup, the identity resolution and the body read, so a refusal still costs a header parse rather than a megabyte. **Six routes beyond the two findings were fixed with them,** because the sweep was done by asking "which handler is given a comp id and writes?" rather than by patching the two files the findings named: `manual-flight.ts`'s three mutations (PUT record, DELETE supersede, POST restore) — a manual flight is evidence for a task in exactly the way a tracklog is, and `submission-gate.ts`'s own header already counts it as the fourth submission call site — and `pilot-status.ts`'s three (PUT upsert, PATCH note, DELETE clear), where absent/DNF/landed feed launch validity (S7F §9.1), so a non-admin writing one into a hidden comp is a scoring input arriving in somebody's unpublished rehearsal. **No hidden-comp write path is left ungated:** every other mutating handler that is given a comp id is `requireCompAdmin`-gated (`comp`/`task`/`pilot`/`waypoints`/`penalty`/`quality-override`/`restore`/`rescore`/`weather-refresh`/`field-analysis-refresh`) or already read `comp.test` (`igc-anon.ts`'s open-submit); the rest are either super-admin (`/api/admin/*`) or not comp-scoped at all (`/api/comp/pilot`, `/api/user/*`).

#### SEC-39 — Anonymous-submission rate-limit budgets chargeable before any legitimacy check — **Medium** — ~~Open~~ **Fixed (2026-08-06, [#556](https://github.com/pokle/glidecomp/pull/556))**

- **Files:** `web/workers/competition-api/src/routes/igc-anon.ts:175-221`.
- **Evidence:** the handler's own comment states the intent — *"Cheapest rejections first. Nothing that costs R2 or CPU runs before something cheaper can turn the request away"* — and charges `ANON_SUBMIT_PER_COMP` (300/24h) at line 178, **before** the competition is confirmed to exist (the `SELECT … FROM comp WHERE comp_id = ?` happens at line 198) and before the pilot identifier is read or matched against the roster at all. `ANON_SUBMIT_PER_PILOT` (6/24h) is charged later in the handler, but still before the file itself is read — so it can be exhausted by a request naming a real pilot's public identifier (per the route's own header comment, "the identifier is a name, not a secret") with no valid file attached.
- **Impact:** `comp_id`/`task_id` only need to decode via the sqids scheme to reach the budget check — they don't need to resolve to a real row — and a real competition's id is visible in its own public URL. An unauthenticated attacker can send up to 300 trivial POSTs a day (no body, no valid identifier headers required) to `/api/comp/<real-comp-id>/task/<any-decodable-id>/igc/open-submit` and exhaust that specific competition's entire daily anonymous-submission allowance, so every subsequent legitimate landing-day pilot at that comp gets `429 rate_limited` for the rest of the day. The route's own fallback ("ask the competition organiser to upload for you") caps how bad this is — the signed-in and on-behalf upload paths are entirely unaffected, since they don't share this budget — which is why this is Medium rather than High: the blast radius is "this one convenience feature stops working for one competition for up to 24 hours," not data loss or an auth bypass. But it does mean the rate limiter — built specifically to bound abuse of this route — is itself the cheapest available abuse of it.
- **Remediation:** charge `ANON_SUBMIT_PER_COMP` only after the competition (and ideally the task) is confirmed to exist, and consider an additional per-IP or per-request-fingerprint budget that doesn't key on attacker-chosen `comp_id`/pilot-identifier values, so a single source can't unilaterally drain a shared, comp-wide counter. (Noted in passing, not a new SEC number: the `rateLimit` table itself has no observed TTL/cleanup job, so a comp-id-keyed counter charged before existence is confirmed also means one new permanent row per distinct decodable id an attacker tries — a slow storage-growth concern, not an acute one, and not a new pattern in this codebase.)
- **Fix (2026-08-06, [#556](https://github.com/pokle/glidecomp/pull/556)).** Analysis and options in [docs/2026-08-05-sec-39-anon-submit-budgets.md](2026-08-05-sec-39-anon-submit-budgets.md). Reordering alone was found **insufficient**: every value the attack needs is public by design — the comp id is in the comp's own URL, the task id on its public page, and a *resolving pilot identifier* on the public roster (`routes/pilot.ts:530` is `optionalAuth`, and its own SEC-15 comment keeps names/IDs/classes public while redacting PII). Reordering therefore raises the attacker's cost from one public value to three and leaves the 300/day drain intact; and it does not touch the sharper case the evidence names but the remediation didn't cover — `ANON_SUBMIT_PER_PILOT` is 6/24 h charged before the body is read, so six empty POSTs naming one pilot's public CIVL id took that pilot's entire landing day. What shipped instead follows `rate-limit.ts`'s own stated intent (budgets that "bound damage rather than … traffic"): the two **damage** budgets are keyed on the victim and so are now charged only after `storeUploadedTrack` succeeds, with a new read-only `peekBudget()` preserving the file's cheapest-rejections-first rule (something at its cap is still turned away before the body is read — on a read, where this previously cost a write); and the miss-only budget is widened into `ANON_SUBMIT_FUTILE`, a per-IP **effort** budget charged on every request that stores nothing. That last is what answers the round's open product question without the trade-off it feared: because a successful submission costs nothing per-IP, a hillside of pilots behind one connection or a CGNAT address is unaffected and only somebody generating failures pays — so a per-IP budget on *every* submission (which would 429 real pilots on exactly the day the route exists for) was considered and rejected. Raised 20→40 since it now covers honest fumbling as well as probing, still far below an enumeration sweep. A 429 deliberately does not charge it. Regression coverage in `test/igc-anon.test.ts`, each case verified to fail against the pre-fix code: a nonexistent comp/task charges nothing, a rejected file charges neither damage budget, and six garbage POSTs naming a real pilot leave that pilot's seventh valid submission working. The peek admits a documented benign race (concurrent requests can all pass it; bounded by concurrency, harmless against 6 and 300 a day). The passing note about `rateLimit` row growth is partly addressed — no row is now created for an id that doesn't resolve — but rows still never expire; a scoped cleanup remains open as gap #21.

#### SEC-40 — Unbounded O(k²) clustering in the new reconstructed-thermals feature — **Low** — Open

- **Files:** `web/engine/src/field-analysis/thermal-shape.ts:653-660` (`findSubCores`).
- **Evidence:** a nested `for i` / `for j = i+1` all-pairs loop clusters a thermal band's upper-quartile-vario samples by pairwise distance via union-find, with no cap on the number of samples compared — the same algorithmic shape SEC-32/33 just fixed elsewhere in the engine, in a file that didn't exist when that sweep ran (`f73f3f9`, landed after `a7202f5`) and so wasn't caught by it.
- **Impact:** mitigated on three sides already in production — field analysis caps total tracks fed into a task's analysis at `MAX_FIELD_ANALYSIS_TRACKS = 80` (SEC-31), `splitOversizedCluster` bounds any one shared-thermal cluster to ≤1800s of flight time before this function ever sees it, and extraction runs on the field-analysis stale-first design's lazy background revalidation path (not blocking a live page-load response, per CLAUDE.md's field-analysis storage rules) — so Cloudflare's per-request CPU cap bounds the blast radius the same way it already bounds every other engine computation. What's missing relative to SEC-32/33's standard: **zero adversarial or DoS regression test coverage** (`web/engine/tests/thermal-shape.test.ts` has none), so there's no evidence pinning down how many colluding/crafted uploads circling at the same place/altitude/time — well within the existing 80-track and 2 MiB-per-file caps — it would take to make this function itself the CPU-cost bottleneck.
- **Remediation:** apply the same treatment SEC-32/33 received — either bound the sample count `findSubCores` compares directly, or restructure to a spatial-grid/bucketed approach that avoids the all-pairs scan — with a before/after oracle test proving output parity, plus a regression test at the scale the original SEC-32/33 write-ups used (tens of thousands of samples) to prove it no longer scales quadratically.
