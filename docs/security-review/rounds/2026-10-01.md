### Executive summary

**The worst finding is SEC-56: email-OTP sign-in could be brute-forced by a
distributed guesser, against any account — including the super-admin, whose
address is in the public source.** Better Auth mints and stores a fresh code,
with three fresh attempts, *before* it calls GlideComp's send hook, so the
per-address send throttle (which lives in that hook) withheld only the email,
never the code. Nothing else counted per account: the remaining limits were
per client address, which Better Auth buckets per IPv6 /64 — and one free
IPv6 /48 is 65,536 of them. A six-digit code then falls in minutes to hours,
bounded only by the attacker's request rate. **Fixed inline** by checking both
per-address budgets in front of Better Auth: no new code for a spent address,
and at most ten refused codes per address per hour from anyone. About ten
guesses an hour against a million codes, each cycle mailing the owner a code
they did not ask for. 7 regression tests fail on the pre-fix code and pass now.

**SEC-55** (Low, fixed inline) is the same root cause seen from the other
side: auth-api handed Better Auth's *whole* endpoint surface to the internet.
That included `/update-user`, which wrote the account name around SEC-49's
checks; `/get-access-token` and `/refresh-token`, which hand out the stored
Google tokens; and `/email-otp/check-verification-otp`, a second code oracle
outside any budget. The catch-all is now an allowlist of the 16
method/path pairs the app's flows use.

The architecture-level findings are **SEC-57** (an API key *is* its account:
no scopes, no expiry, can mint further keys and delete the account),
**SEC-58** (every Pages deployment ever built is a production trust domain:
bound to production data, a trusted origin for production auth, and never
expiring), and **SEC-59** (one account-wide Cloudflare token is reachable from
every branch's deploy job, behind tag-pinned third-party actions). The
proposals that answer them are in "Architecture" below. `bun audit` is clean;
SEC-52 held. No Critical findings.

### New findings

#### SEC-56 — Email-OTP sign-in brute-forceable by a distributed guesser — **High, fixed inline**

**Files.** `web/workers/auth-api/src/auth.ts` (`sendVerificationOTP`),
`src/rate-limit.ts`, `src/index.ts`; upstream
`better-auth/dist/plugins/email-otp/routes.mjs` (`resolveOTP`,
`atomicVerifyOTP`), `@better-auth/core/dist/utils/ip.mjs` (`normalizeIP`).

**Evidence.**
1. `POST /email-otp/send-verification-otp` calls `resolveOTP()`, which
   generates and **stores** a new code (`value: "<hash>:0"` — zero attempts
   used) and only then calls our `sendVerificationOTP` hook. The per-address
   throttle (`registerOtpEmailSend`, 5 per 15 minutes) ran inside that hook,
   so past the cap it returned without emailing — and left the new code in
   D1. Each refused request gave a guesser a fresh code and three tries.
2. Nothing else was keyed on the account. The remaining limits — 3 sends and
   5 verifies per minute — are Better Auth's per-IP `customRules`, keyed on
   `cf-connecting-ip` and normalised to a /64 for IPv6. A tunnel-broker /48
   is free and holds 65,536 /64s. Residential proxy pools are cheap.
3. Per code, `atomicVerifyOTP` is sound (atomic consume, three attempts), so
   the guess rate is simply 5 per client address per minute, times however
   many addresses the attacker has. Expected guesses to 50% success: ~693,000.
   At 100 guesses/s that is about two hours; at 1,000/s, about twelve
   minutes. The only signal to the victim was ≤ 5 code emails per 15 minutes.

**Impact.** Account takeover of any address, unauthenticated and remote. For
`SUPER_ADMIN_EMAILS` (`super-admin.ts`, public) that is admin of every
competition: scores, rosters, deletion, every pilot's email. Rated High, not
Critical, because it takes sustained distributed effort, D1 throughput caps
the rate in practice, and the zone's own bot and rate protections are
unverified (G-03).

**Remediation (applied).**
- `index.ts` now registers handlers ahead of the Better Auth catch-all for
  the two OTP endpoints. On send it **peeks** the per-address budget
  (`otpSendAllowed`, read-only) and answers `{"success":true}` without
  calling Better Auth when it is spent, so no code is minted. The hook still
  **charges** it (`registerOtpEmailSend`), atomically, so emails stay capped
  at exactly five. Only `type: "sign-in"` is accepted.
- On sign-in it peeks a new per-address **failure budget**
  (`OTP_VERIFY_FAILURE_BUDGET`: 10 per hour, key `otp-fail:<email>`) and
  answers 429 + `Retry-After` when spent, even for the right code. After
  Better Auth answers, it charges the budget only for `INVALID_OTP`,
  `OTP_EXPIRED` or `TOO_MANY_ATTEMPTS`. A per-IP 429 checked no code, and a
  malformed body names no account worth a row.
- Both guards read a JSON body from a clone of the request. Any other body
  is a 415 (Better Auth's router refuses non-JSON here too today; the guards
  don't rely on it). Addresses longer than 254 characters are a 400 before
  any row is touched.
- The window stays ≤ 1 day, so `purgeExpiredAuthData`'s two-day `rateLimit`
  retention still covers it.
- Tests (`test/email-otp.test.ts`, "SEC-56" block, every request from its own
  client address): a throttled send leaves no code row; ten wrong codes from
  ten addresses, then a fresh *correct* code from an eleventh, gets 429 with
  `Retry-After` and no cookie; another address is untouched; a right first
  code charges nothing; non-sign-in types mint nothing; non-JSON bodies are
  415. `e2e/email-otp-signin.spec.ts` (manual code, deep link, wrong-code
  retry, per-IP 429) passes unchanged.

**Residual.** About ten guesses an hour per address (plus up to one live
code's three attempts when a burst races the peek). That is ~8 years of
continuous guessing for a 50% chance, while mailing the owner 4+ unrequested
codes an hour. An attacker can lock an address out of *code* sign-in for an
hour with ten junk requests. Google sign-in is unaffected, and the send
throttle already allowed a similar nuisance. Lower it further with an 8-digit
code or Turnstile (A8). The sign-in page shows its existing per-IP 429 text
for the new 429, which understates an hour. No copy was changed; new
wording is the owner's call. The whole block in `SignIn.tsx`'s `verify()`,
with the proposed new case (the response's `code` is `TOO_MANY_REQUESTS`,
distinct from Better Auth's own codes):

| When | Shown today | Proposed |
|---|---|---|
| `OTP_EXPIRED` | That code has expired. Send yourself a new one. | (unchanged) |
| `TOO_MANY_ATTEMPTS` | Too many attempts with that code. Send yourself a new one. | (unchanged) |
| per-address 429 (new) | Too many tries in a row. Wait a minute, then try again. | Too many wrong codes for this address. Try again in an hour, or sign in with Google. |
| per-IP 429 | Too many tries in a row. Wait a minute, then try again. | (unchanged) |
| anything else | That code didn't work. Check it and try again. | (unchanged) |

#### SEC-55 — The Better Auth catch-all served the library's whole endpoint surface — **Low, fixed inline**

**Files.** `web/workers/auth-api/src/index.ts` (catch-all), new
`src/endpoints.ts`.

**Evidence.** `app.all("/api/auth/*")` forwarded every path to
`auth.handler`. The configured plugins mount 47 endpoints; the app's flows need 16
method/path pairs. Live but unused:
- `POST /update-user` — `{name, image}` with `z.any()` values. It wrote
  `"user".name` (the public audit log's `actor_name`) with none of SEC-49's
  checks: control characters, `<`/`>`, any length up to the 128 KiB body cap.
  It also took an arbitrary `image` URL. **SEC-49's fix was therefore
  incomplete**: it validated the two routes GlideComp wrote, not the one the
  library already served.
- `POST /sign-in/email-otp` with a first-time `name`/`image` — the same
  bypass at sign-up.
- `POST /get-access-token`, `POST /refresh-token`, `GET /account-info` — hand
  the stored Google OAuth tokens (kept in plaintext in `account`) and
  profile to any session or API key.
- `POST /email-otp/check-verification-otp` — tests a code without signing in.
  A second oracle outside SEC-56's budget. The other email-OTP flows
  (verify-email, forget/reset-password, email change) mint and consume codes
  of types the app never uses.

**Impact.** Defence-in-depth bypasses (React still encodes the name at every
sink) and a wider token-exposure path for an XSS or a leaked API key. Low on
its own; the oracle matters for SEC-56.

**Remediation (applied).** `src/endpoints.ts` lists the method/path pairs the
catch-all serves: Google sign-in and its callbacks, the two OTP endpoints,
`/get-session`, `/sign-out`, `/jwks`, API-key create/list/delete, `/error`,
`/ok`. Everything else under `/api/auth/` is a 404. The sign-in guard
(SEC-56) also refuses a body carrying `name` or `image`. Tests
(`test/endpoints.test.ts`): a unit table of served and refused pairs; HTTP
404s for `/update-user` (with the name verified unchanged), the three token
endpoints and the check oracle; Google sign-in still starts, the callback is
still routed, `/jwks`, `/get-session` and `/ok` still answer.
`docs/api.md` and `docs/auth.md` now name the served set.

**Residual (G-27).** A first Google sign-in still copies Google's profile
name straight into `"user".name`. The complete fix is to run every Better
Auth user write through `isValidNameText()` in
`databaseHooks.user.create.before`/`update.before` (blank an invalid name, so
onboarding asks for one).

#### SEC-57 — An API key is its whole account: no scopes, no expiry, mints keys, deletes the account — **Medium, open**

**Files.** `web/workers/auth-api/src/auth.ts` (`apiKey({
enableSessionForAPIKeys: true })`), `src/index.ts` (`/delete-account`),
`web/frontend/src/react/pages/Settings.tsx` (`ApiKeysSection`), `docs/api.md`.

**Evidence.** The api-key plugin's `before` hook turns an `x-api-key` header
into a full session on *every* Better Auth endpoint, and our custom routes
accept it too because they ask `auth.api.getSession()`. Keys are created
with only a name. The plugin's `permissions` go unused, and
`keyExpiration.defaultExpiresIn` is `null`, so keys never expire. A key can
therefore create more keys (persistence that survives revoking the first),
revoke the owner's keys, and `POST /delete-account`, which deletes the user
and every R2 object under `u/<id>/`. It can also act as comp admin on every
competition the owner administers (all of them, for a super admin). Settings
offers keys to "scoring agents". Where such an agent is an LLM reading
untrusted text, the key's blast radius is exactly what a prompt injection
inherits.

**Impact.** One leaked or misused key = permanent, total account compromise.

**Remediation (proposed — A3).** (1) Refuse API-key sessions on
`/api-key/*`, `/delete-account`, `/set-username` and `/set-name`: account
management needs a browser session. Small, but it changes documented
behaviour (`docs/api.md` lists `delete-account` among the key-usable
routes), so it is the owner's call. (2) Default expiry (90 days) and a
"last used" column in Settings. (3) Scopes via the plugin's server-only
`permissions`, chosen at creation: `read`, `submit` (tracks), and
`comp-admin` limited to named comps. competition-api reads them from `/me`
and gates with a `requireScope()` middleware. (2) and (3) need Settings copy
the owner signs off.

#### SEC-58 — Every Pages deployment is a production trust domain, and none ever expires — **Medium, open (needs live verification, G-24)**

**Files.** root `wrangler.toml` (service bindings, no `[env.preview]`),
`.github/workflows/deploy.yml` (Pages deploy on every pushed branch),
`web/workers/auth-api/src/auth.ts` (`trustedOrigins`, `oAuthProxy`),
`web/workers/shared/src/cors.ts` (`PAGES_PREVIEW`, `localhost`).

**Evidence.**
- Previews bind the production workers, and so production D1/R2 ("Branch
  previews reuse the already-deployed production Workers via their service
  bindings").
- Production auth trusts `https://*.glidecomp.pages.dev` (`trustedOrigins`)
  and production CORS admits `^https://[a-z0-9-]+\.glidecomp\.pages\.dev$`
  with credentials. `oAuthProxy` completes a *production* Google sign-in onto
  any such origin (`/callback/:id/oauth-proxy`).
- Cloudflare Pages serves every deployment at its own
  `<hash>.glidecomp.pages.dev` URL until it is deleted, and nothing in the
  repo deletes any. Each deployment keeps the client code and `_headers` it
  was built with. So builds before 2026-09-27 carry **no enforced CSP** (it
  was `Content-Security-Policy-Report-Only` until #718), and builds before
  2026-08-17 carry one or more of the SEC-22/41/47 stored-XSS sinks.
- `pages.dev` is on the Public Suffix List, so every
  `*.glidecomp.pages.dev` host is **same-site** with every other:
  SameSite=Lax does not separate one deployment from another.
- Production CORS also admits any `localhost` origin, which no production
  caller needs.

**Impact.** The set of origins production trusts only grows, and each keeps
its oldest bugs. Any client-side vulnerability that ever shipped stays
reachable on its hash URL against production data. Through `oAuthProxy`, a
script on any of those origins can walk a visitor through Google sign-in
(silent when they have one Google account and prior consent) and act as
them. No working chain is shown this round: the pre-#666 analysis page
needed a session on that host, and name fields now refuse `<`. Hence Medium,
pending a live look at which deployments still answer.

**Remediation (proposed — A1).** *Now:* enable Cloudflare Access on preview
deployments (Pages → Settings → "Enable access policy"; check it also covers
production deployments' hash URLs). Add a scheduled job that deletes
deployments older than ~30 days, keeping current production and the latest
per branch. *Next:* implement `docs/preview-environment-plan.md` (preview
workers + D1 + R2). Then remove `*.glidecomp.pages.dev` and `localhost` from
production `trustedOrigins` and `isAllowedOrigin` (dev builds keep
localhost), and drop `oAuthProxy` from the production config. The plan
predates this finding and is written for convenience; this is the security
case for doing it.

#### SEC-59 — One account-wide Cloudflare token behind tag-pinned actions, reachable from every branch — **Medium, open**

**Files.** `.github/workflows/deploy.yml`, `civl-rankings.yml`, `claude.yml`.

**Evidence.**
- `CLOUDFLARE_API_TOKEN` is one token for Pages, Workers and remote D1
  (`civl-rankings.yml` relies on it carrying D1 edit). The deploy job hands
  it to `wrangler-action` on every pushed branch, after `bun install` and
  `bun run build` of that branch's code have run in the same job.
  wrangler-action prefers the project's own `node_modules/wrangler`, so code
  that ran earlier in the job decides what later holds the token.
- Third-party actions are pinned to mutable tags (`oven-sh/setup-bun@v2`,
  `cloudflare/wrangler-action@v3`, `anthropics/claude-code-action@v1`, and
  `actions/*` too). There is no top-level `permissions:`, so the test and e2e
  jobs get the repository's default token.
- `civl-rankings.yml` is `workflow_dispatch`-able from any branch, with the
  token in the environment of a `bun run` step.
- `claude.yml` gives an agent `contents: write`. The agent acts on issue and
  PR text anyone can write, and any branch it pushes deploys with the same
  token.

**Impact.** One compromised action tag (the tj-actions/changed-files incident
of March 2025), one malicious dependency, or one prompt-injected agent push
yields an account-wide Cloudflare token: production D1, R2 and Workers.

**Remediation (proposed — A6).** Two tokens. A Pages-only token for preview
deploys; the production token (Workers + D1 + Pages) in a GitHub Environment
`production`, limited to `master`. Build in a job with **no** secrets, upload
the artefact, deploy from a job that installs nothing. Pin actions by full
commit SHA, with Dependabot's `github-actions` ecosystem to bump them. Add a
top-level `permissions: contents: read`. Guard `civl-rankings`' dispatch with
`if: github.ref == 'refs/heads/master'`. For `claude.yml`, gate on
`author_association` and treat issue bodies as untrusted input to the agent.

#### SEC-60 — Worker responses carry no hardening headers; 500s echo exception text — **Low, open**

**Files.** `web/workers/{auth-api,competition-api,airscore-api}/src/index.ts`,
`competition-api/src/routes/waypoints.ts`.

**Evidence.** On production, `glidecomp.com/api/*` is served by the workers'
own `[[routes]]` and never touches Pages, so neither `_headers` nor
`_middleware.ts` applies. No worker sets `X-Content-Type-Options`, a CSP or
`Cross-Origin-Resource-Policy`. Waypoint files go out `inline` as
`application/gpx+xml` / KML from the app origin. An XML document can run an
XHTML `<script>`, so that is safe only while `xmlEscape()` stays correct
(it is). `app.onError` in auth-api and competition-api returns
`err.message`; D1 errors carry SQL and constraint text.

**Remediation (proposed — A5).** One `worker-kit/secure-headers` middleware
on every worker: `X-Content-Type-Options: nosniff`,
`Content-Security-Policy: default-src 'none'; frame-ancestors 'none'; sandbox`
(a document no API response ever needs to execute),
`Cross-Origin-Resource-Policy: same-origin` (airscore's public GETs
excepted), `Referrer-Policy: no-referrer`. 500s become a generic message
with a request id; the detail stays in the logs.

#### SEC-61 — "Internal" routes are private only by an implicit wrangler default; the AirScore proxy is unthrottled — **Low, open (live check G-25)**

**Files.** `web/workers/airscore-api/src/index.ts` (`/internal/cache/*`), all
three worker `wrangler.toml`s; `node_modules/wrangler` `getSubdomainValues()`.

**Evidence.** airscore-api serves unauthenticated `GET /internal/cache/stats`
and `POST /internal/cache/clear`, and `docs/api.md` promises `/internal/` is
"not routable from the internet". No config sets `workers_dev` or
`preview_urls`. wrangler 4.116 defaults `workers_dev` to `false` only
*because* `[[routes]]` exist, and leaves `preview_urls` at whatever the
dashboard holds. The public `/api/airscore/*` proxy has no rate limit
(BUG-26 in 2026-04-20, never registered): every new numeric `trackId` is an
upstream fetch and a KV write. competition-api's `AIRSCORE_API` binding is
used only by the super-admin cache page.

**Remediation (proposed).** `workers_dev = false` and `preview_urls = false`
in all three worker configs (no change if the live state is already off;
verify first, G-25). A Workers Rate Limiting binding on the AirScore proxy.

#### SEC-62 — Personal-library task links are guessable — **Info, open**

**Evidence.** `GET /api/u/:username/task/:task_code` is "public by link", but
usernames are public and task codes are user-chosen (`t1`, `day-2`). Tracks
are keyed by a SHA-256 of their content, which is unguessable; tasks are
not. **Remediation.** If a library task can be sensitive (set before a
briefing), add a random share token; otherwise document it as public.

### Architecture

What is **already strong** — keep it: asymmetric JWKS session-cache
verification (no worker but auth-api can sign anything), parameterised SQL
everywhere, bounded Zod schemas and body caps, the enforced CSP with no inline
script, the peek/charge budget idiom, the sink-pin and doc-coverage tests,
`private, no-store` on every cookie-forwarded SSR render, and a public audit
log for every scoring mutation. None of the proposals below replaces any of
them.

The proposals, by leverage. "Closes" names the findings each retires as a
*class*, not one instance.
