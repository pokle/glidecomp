### New findings

#### SEC-51 — Public waypoint-CSV export missing the shared formula-injection guard — **Medium, fixed inline**

**Files.** `web/engine/src/waypoint-export.ts` (`csvField`, `toCSV`,
`toSeeYouCup`); served by
`web/workers/competition-api/src/routes/waypoints.ts` (`fileResponse`, the
two `GET .../waypoints/:format` routes).

**Evidence.** `toCSV()` wrote `code`/`name` through `csvField()`, which only
quotes a field containing a comma, double-quote or newline:

```ts
function csvField(s: string): string {
  return /[",\n]/.test(s) ? `"${s.replace(/"/g, '""')}"` : s;
}
```

A waypoint named `=cmd|'/c calc'!A0` (or any string starting `=`/`+`/`-`/`@`)
passes straight through. The two routes serving it are `optionalAuth` —
public, unauthenticated, for any competition that isn't a hidden `test`
comp — respond `Content-Type: text/csv;charset=utf-8` with
`Content-Disposition: inline`, and the `code`/`name` Zod validation
(`noControlChars.max(128)`) has no leading-character restriction. This is
the identical vulnerability class already fixed three times in this
codebase (SEC-28 pilots CSV, SEC-36 CIVL-rankings CSV, SEC-43 route-editor
CSV), all via the shared `csvEscape()` in `src/react/comp/csv.ts` — this
sink used the engine's own, older `csvField()` instead and was never
brought into line.

**Impact.** A comp organiser (who can edit the waypoint set, or upload a
waypoint file containing arbitrary code/name strings) sets a waypoint's name
or code to a formula/DDE payload. Any visitor to the public comp — a pilot,
a spectator, anyone with the comp's URL — who downloads the `.csv` export
and opens it in Excel or Sheets executes that payload (a `HYPERLINK`
exfiltration to a URL, or, via the DDE `=cmd|...!...` form on older
Excel, an actual command). No authentication is required to trigger the
download; the write side (setting the waypoint name) is already
`requireCompAdmin`, so the practical actor is a comp organiser targeting
their own pilots/spectators, or an organiser account compromised by some
other means using this as a second-stage payload delivery.

**Remediation (applied).** Added `csvFieldGuarded()` — `csvField()` with the
same leading-character prefix rule `csvEscape()` uses
(`/^[=+\-@\t\r]/` → prefix `'`) — and switched `toCSV()`'s two field writes
to it. Left `csvField()` (and `toSeeYouCup()`, which shares it) unchanged
**by design**: SeeYou `.cup`, CompeGPS, OziExplorer and the FS formats are
all served `application/octet-stream` with a device-specific extension —
none of them is handed to a spreadsheet app by a browser's default file
handler — and are read literally by flight-instrument software as the
waypoint's own identifier, where a `'` prefix would corrupt a legitimate
dash-leading code (e.g. `-15`) rather than protect anyone. Guarding only
the format that is actually `text/csv` mirrors the precedent
(`csvEscape()` guards the pilots/rankings/route-editor CSVs, which are
also genuinely spreadsheet-bound) rather than widening the change to
formats where it would be a regression, not a fix.

**Regression test.** `web/engine/tests/waypoint-export.test.ts` — a new
case asserts `toCSV()` prefixes `'` onto a `=`/`+`/`-`-leading code and name
and that the SeeYou `.cup` writer is untouched for the same input. `bun
test web/engine` (77 files) and the full `test:all`/`typecheck:all` runs
above are green with this change in place.
