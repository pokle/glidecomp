### Executive summary

**Two findings, both fixed inline.** The more consequential is **SEC-50**, a
`bun audit` regression to 13 vulnerabilities (1 critical, 6 high) — over
four times the residual every round since 2026-08-12 has carried. Unlike
SEC-48 (a dependency *upgrade* widening resolution past a stale override),
this round's growth had no code cause at all: it is what happens when the
public vulnerability database grows against packages a lockfile is quietly
holding at an old-but-still-range-satisfying patch release, and nothing in
the weekly dependency-upgrade cycle or this review's own `bun audit` step
had forced a re-resolution since. The clearest example: `hono` — the actual
HTTP framework every one of the four Workers (auth-api, competition-api,
airscore-api, and the frontend's dev tooling) runs on — had two moderate
CVEs against `4.13.3` (an unbounded-nesting `parseBody()` memory-exhaustion
DoS reachable by any caller who can POST a JSON body to a public API route,
and a query-string parsing differential), both fixed in `4.13.5`, sitting
unaddressed in the lockfile despite `4.13.7` already existing and already
satisfying the project's own `^4.13.3` range in both the root dependency
entry and the `overrides` block. `js-yaml`, `sharp` and `svgo` (all
transitive, via `astro`) carried the same pattern. **Fixed by bumping five
`package.json` overrides to their available patched releases** — `hono`
`^4.13.3`→`^4.13.7`, `js-yaml` `^4.3.1`→`^4.3.2`, `sharp` `^0.35.3`→`^0.35.4`,
`svgo` `^4.0.2`→`^4.1.0`, and a new `smol-toml: ^1.8.0` override — all
patch-level, no breaking-change upgrade, `bun run typecheck:all` and
`bun run test:all` green afterward with unchanged counts. The residual after
the fix is 5 advisories, all `astro` (`<7.0.6`) — the pre-existing SEC-34/
G-16 gap, whose composition happens to now include a newly-disclosed
Critical (RCE via AVIF image optimisation). Traced its reachability:
`<Picture>`, astro's image-optimisation component, is used only over
hand-authored images checked into the repo, invoked only at `bun run build`
time — never on a user-supplied image, never in the deployed runtime — so
it stays classified dev/build-time-only and not currently exploitable, but
a Critical CVE sitting in an unaddressed residual across (as of this round)
six rounds running is a materially worse position than "3 moderate/low
astro advisories," and this round elevates the `astro` 6→7 upgrade (G-16)
in urgency accordingly, even though it remains out of scope for a
same-round override fix.

**SEC-50 differs from SEC-48 in a way worth a standing scope gap of its
own**: SEC-48 was closed by tightening an override that a dependency bump
had outrun; this round shows that even with no dependency bump at all, a
lockfile can silently drift behind newly-available patch releases within
its own declared ranges, because neither `bun install` nor a bare `bun
update <pkg>` re-resolves an already-satisfied entry to the latest
matching version — only `bun update <pkg> --latest` (or a manually
tightened override, as applied here) does. Logged as **G-20**: the weekly
`upgrade-deps` cycle's own `bun audit` check evidently did not catch this
between rounds either (the 2026-08-23 log's claim of "no new" vulnerabilities
was already the SEC-48 finding's root cause, and this round shows the same
gap persists for CVEs disclosed against already-installed versions, not
just ones introduced by a bump) — worth deciding whether `upgrade-deps`
should routinely re-resolve in-range dependencies to latest-patch rather
than relying on `bun install`'s conservative default.

**SEC-49, documented last round as a small Info-grade follow-up, is now
fixed.** `POST /api/auth/set-name` and the pre-existing `set-username` write
directly to `"user".name` — read back as the public audit log's
`actor_name` — with only a length check, while every other user-entered
comp/pilot/task name field got the SEC-22 defence-in-depth control-char/
angle-bracket/NFC treatment in #232 the round before. Closed by extracting
that check into `web/workers/shared/src/name-text.ts`
(`@glidecomp/worker-kit/name-text`), the same cross-worker package pattern
already used for CORS and rate-limiting, and wiring both auth-api routes
through it ahead of their writes. Four new regression tests in
`web/workers/auth-api/test/routes.test.ts` cover both routes rejecting an
angle-bracket payload and a raw control character, and confirm the
account's prior name is left untouched on rejection (the existing "refuses
a blank name" pattern this file already used for the length check).
competition-api's own validators were already correct and untouched.

Nothing else new this round. The `CompSectionNav` rollout (#687) and the
super-admin "Organised by" credit exclusion (#690) both got a full read
given they touch the admin/authorisation-adjacent surface, and both are
confirmed display-only changes that do not alter `is_admin`/`isCompAdmin`
authorisation. SEC-45 remains untouched, now four rounds running without a
fix PR started.

### New findings

advisories (13 vulnerabilities, 1 critical) surfaced by newly-disclosed
CVEs against already-locked, range-satisfying dependency versions (High,

- **Files:** `package.json` (root `overrides` and the `hono` `dependencies`
  entry), `bun.lock`.
- **Evidence:** `bun audit` on the unmodified `2c34721..345fa81` HEAD
  reported: `hono@4.13.3` (moderate ×2 — `GHSA-gqvv-2mrq-wpjv` incomplete
  `toSSG()` path-traversal fix, `GHSA-g6gw-c38x-mqfc` unbounded
  dot-notation nesting in `parseBody()` causing memory exhaustion,
  `GHSA-crvj-82cr-hjcx` query-parameter/fragment cache-key differential —
  all fixed in `4.13.5`, four Workers workspaces affected: `@glidecomp/
  frontend`, `airscore-api`, `auth-api`, `competition-api`), `js-yaml`
  (`>=4.0.0 <4.3.2`, high — `GHSA-2883-xcg3-v3hh`, `maxTotalMergeKeys` CPU
  exhaustion), `sharp` (`<0.35.4`, high — `GHSA-rgj7-g3m4-5g8c`, libheif
  vulnerabilities), `svgo` (`>=4.0.0 <4.1.0`, moderate + high —
  `GHSA-4vpr-x523-8j87`/`GHSA-w27v-7q3p-w38r`, incomplete `removeScripts`
  script sanitisation), `smol-toml` (`<=1.7.0`, high —
  `GHSA-7w5x-hrqm-74c2`, malformed-TOML DoS), plus the 3 pre-existing
  `astro` advisories. Root-caused to time, not to any commit: `git diff
  2c34721..345fa81 -- package.json bun.lock` is empty, and `bun update
  hono` (no `--latest`) left the lockfile at `4.13.3` even though
  `4.13.4`–`4.13.7` all exist on the registry and satisfy the project's own
  `^4.13.3` constraint (confirmed directly against `registry.npmjs.org`
  through the environment's configured proxy) — bun's default resolution
  preserves an already-range-satisfied lockfile entry rather than
  advancing it, so newly-disclosed CVEs against an old-but-in-range patch
  version accumulate silently until something explicitly forces
  re-resolution.
- **Impact:** The `hono` findings are the ones that matter — `hono` is the
  actual HTTP framework auth-api, competition-api and airscore-api run on
  in production, not a dev-time tool like the SEC-48/SEC-34 packages. The
  `parseBody()` memory-exhaustion advisory in particular describes a DoS
  reachable by any caller able to POST a JSON body with deeply-nested
  dot-notation keys to a public API route — real, if bounded in blast
  radius by the SEC-06 body-size cap and Workers' own per-request memory
  ceiling. `js-yaml`/`sharp`/`svgo`/`smol-toml` are all transitive via
  `astro` (build-time only, same reachability analysis as SEC-34) or, for
  `js-yaml`, also via the confirmed-unused `shadcn` devDependency
  (SEC-48's package).
- **Remediation (applied):** `package.json` — bumped the `hono` root
  `dependencies` entry and `overrides` entry `^4.13.3`→`^4.13.7`
  (consistent, no split versions), `js-yaml` `^4.3.1`→`^4.3.2`, `sharp`
  `^0.35.3`→`^0.35.4`, `svgo` `^4.0.2`→`^4.1.0`, added `smol-toml: ^1.8.0`
  (no prior override). All five are patch/minor releases within the
  already-declared major version — no API surface change, confirmed by
  `bun run typecheck:all` and `bun run test:all` staying green with
  unchanged pass counts. `bun audit` re-run: down to 5 advisories, all
  `astro` (the SEC-34/G-16 residual — see Executive Summary for its
  reachability and the new Critical it now includes).
