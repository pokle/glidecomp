### Executive summary

**Two new Mediums and one new Low; no Critical/High; every prior fix intact.** The two headline new surfaces are both well-built. **Task weather** adds the project's first outbound third-party fetch, and it is SSRF-safe by construction (hardcoded provider hosts; the only variable inputs are numeric lat/lon, `.toFixed(4)` + `encodeURIComponent`), never blocks a page render (cold path schedules a background fetch and returns `pending`), is admin-gated on its one mutation, and correctly does not touch the score cache (weather is invalidated by query-key). **Field analysis going public + SSR'd** mirrors the score route's visibility and cache rules exactly — a hidden `test` comp still 404s for anonymous callers and its report body can never enter a shared cache. The new organizer `weather_notes` free-text is bounded (4000 chars), audit-logged as an excerpt, and rendered as React-escaped text with no HTML sink. The worst new finding is **SEC-32 (Medium)**: the new `altitude-cleaning.ts` cross-channel rolling-median loop is O(N² log N) when an uploaded IGC packs all its fixes into a single ≤120 s window (e.g. every B-record stamped the same `HHMMSS`, which the parser never rejects) — a crafted ~60k-fix file drives ~6×10¹⁰ ops synchronously on the parse path that runs for **every** upload. It is Medium not High because Cloudflare's per-request 30 s CPU cap and per-request isolation bound the blast radius, and the poison detonates *before* `R2.put` so it is never stored (it cannot wedge other pilots' scoring). **SEC-33 (Low)** is the same root cause in track-quality's "never airborne" glide window. Both live in `SCORING_ROOTS`, so a fix requires a `SCORING_ENGINE_VERSION` bump and gap-2018 parity re-validation, and no output-preserving one-liner exists (the real fix is an incremental sliding-window median) — deferring them was the right call for an unattended review PR rather than risking a silent scoring change. **SEC-34 (Medium)** is a newly-dirty `bun audit` (11 advisories, all in **dev/build-time** tooling — shadcn CLI, concurrently, vite, wrangler, astro build, sharp, vitest-pool-workers — none reachable in the production Workers runtime); two lapsed overrides (shell-quote, postcss) were refreshed inline to clear 2 highs, and the remaining 7 (needing major bumps of astro/react-router/sharp/fast-uri/@hono-node-server/brace-expansion) are deferred to the weekly `upgrade-deps` routine, which does the build verification a security PR shouldn't attempt unattended. Everything else — CORS allowlist, `isLocalDev` gating, IGC caps, no internal-user header, super-admin gate, `_headers` — is unchanged and intact.

### New findings

#### SEC-32 — Quadratic-time altitude cleaning on crafted/degenerate IGC timestamps — **Medium** — Open (tracked in [#470](https://github.com/pokle/glidecomp/issues/470); deferred — `SCORING_ROOTS`)

- **Files:** `web/engine/src/altitude-cleaning.ts:142-163` (`crossChannelClean`, the ±60 s rolling-median baseline), reached unconditionally from `cleanAltitudes()` (`:108`) inside `parseIGC()` (`igc-parser.ts:414`).
- **Evidence (subagent, confirmed):** the loop advances two monotone pointers `lo`/`hi` on the assumption that `times[]` is ascending, then for each of `n` fixes rebuilds a `window` array (`:145-148`) and `window.sort()`s it (`:150`). The IGC parser does **not** enforce monotonic or de-duplicated fix timestamps (`dayOffset` only ever increments; identical `HHMMSS` across all B-records yields identical `times[]`). When every fix shares one timestamp `T`, `lo` never advances (`T < T−60000` is false) and `hi` jumps to `n` on the first iteration and stays there, so every outer iteration builds and sorts a full length-`n` window → **O(N² log N)**. At the 2 MiB decompressed cap (~60k fixes) that is ~6×10¹⁰ operations — a synchronous multi-second-to-CPU-limit hang. The pathological trigger is any file whose fixes all fall inside one ≤120 s span (identical or densely-repeated seconds) with non-zero GNSS **and** baro altitudes (so both channels read "alive" at `:105-108` and route into `crossChannelClean`). Craftable within the parser's accepted input; not reachable by a normal multi-hour flight, whose real time-spread keeps each window bounded.
- **Impact:** CPU amplification on the IGC parse path, which runs for **every** upload (`igc.ts:327`, before `R2.put` at `:337`). **Bounded** by: (a) Cloudflare's per-request 30 s CPU limit (`wrangler.toml [limits] cpu_ms`), which terminates the request rather than hanging the isolate; (b) per-request isolation, so it does not degrade other users' requests; (c) the poison detonating *before* the R2 write, so it is never stored and therefore cannot wedge the task's later score computes (which only parse already-stored, already-successfully-parsed tracks). This is why it is **Medium**, not High — a repeatable per-request CPU/cost sink (reachable on open comps that accept uploads without pilot listing, cf. SEC-04), not a stored-poison scoring outage or a cross-tenant hang.
- **Why not fixed inline:** `altitude-cleaning.ts` is in `SCORING_ROOTS`, so any edit requires a `SCORING_ENGINE_VERSION` bump and gap-2018 parity re-validation, and there is **no output-preserving one-liner** — a naive window/fix-count cap changes the computed median (hence the `cleanedAltitude` that feeds scoring) for dense-but-legitimate high-rate tracks. The correct fix is an **incremental sliding-window median** (two heaps / order-statistic structure), O(N log N) and value-identical, which is a non-trivial rewrite unsuitable for an unattended security PR. Deferred to an engine-owner change.
- **Remediation (next round / engine owner):** replace the per-iteration full sort with an incremental sliding-window median (identical output, O(N log N)); and/or reject or coalesce non-monotonic / duplicate-timestamp fixes at parse time; add a fuzz/regression test asserting a 60k-fix single-second file parses in bounded time. Bump `SCORING_ENGINE_VERSION` and re-run `bun web/scripts/verify-airscore-parity.ts corryong-cup-2021-open-t1`.

#### SEC-33 — Quadratic-time track-quality "never airborne" glide window — **Low** — Open (tracked in [#471](https://github.com/pokle/glidecomp/issues/471); deferred — `SCORING_ROOTS`)

- **Files:** `web/engine/src/track-quality.ts:838-869` (`checkNeverAirborne`, the S2 sustained-glide scan), inner min-speed recompute at `:846`.
- **Evidence:** the outer window is bounded by **time** (`AIRBORNE_GLIDE_SECONDS = 90 s`, `:840`), not by fix count, and the inner loop `for (j = lo+1; j <= i; …)` (`:846`) re-scans the whole window per qualifying `i`. Pack ~57k fixes into a ~100 s span (with flat altitude so `climbFound`/`glideFound` stay false and the `break` at `:867` never fires) and it is ~3×10⁹ integer compares — O(N²) on untrusted-sized input in the scoring path (`assessTrackQuality`, called from `scoring.ts`). Same root cause as SEC-32 (time-bounded window, no fix-count bound). Cheaper per iteration (integer compares, no sort/alloc) and gated behind the two HARD checks (the file must carry a correct local date and a fix within 100 km of a turnpoint to reach this SOFT check), hence **Low**.
- **Impact:** additional CPU on the score-compute path for a crafted stored track. Note this one *can* be reached at score time — but only for a track that already passed upload parsing (i.e. it must not have tripped SEC-32 at upload), so in practice the two are hard to trigger together on the same file. Platform-bounded per request as SEC-32.
- **Remediation:** bound the S2 window by fix count as well as time (or maintain a running window-min), same `SCORING_ENGINE_VERSION` + parity requirement as SEC-32; fix alongside it.
