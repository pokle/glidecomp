### Executive summary

**One new finding, Low (SEC-29):** the new client-side waypoint-file importers `parseWaypointsGPX` / `parseWaypointsKML` (`web/engine/src/waypoint-files.ts`) use lazy `[\s\S]*?` regexes with no matched-close bound, so a crafted file of many unclosed `<wpt>` / `<Placemark>` openings makes each match rescan to end-of-string — O(N²), a few-MB file freezes the tab for minutes. It is reachable only from the browser of the user who *selects their own file* (`CompWaypoints.tsx` `await file.text()`); no Worker or Pages Function parses raw waypoint files (grep-confirmed), and only the structured `WaypointFileRecord[]` is ever persisted — so it is a self-inflicted browser hang, not a cross-user or server DoS. Documented and deferred per the Low-severity policy. **Everything else came back clean.** The SSR public-pages surface — flagged last round as the thing to re-review if it ever landed — is the largest new attack surface and was built defensively: `serialize()` escapes `<`/`>`/`&`/U+2028/U+2029 (blocking both `</script>` and `<!--` breakout for `window.__SSR_DATA__` and every JSON-LD block), the `<title>`/meta/canonical tags run through `escapeHtml`/`escapeAttr`, every loader interpolates path segments via `encodeURIComponent`, cookie-forwarded (admin/test-comp) renders carry `Cache-Control: private, no-store` so visitor-specific data can't land in a shared cache, and any loader/render error falls back to the plain SPA shell so SSR can never make a page *less* available. All eight new/changed mutating handlers (manual-flight PUT/DELETE/restore, waypoints PUT, igc restore, pilot-status PUT/PATCH/DELETE) carry `requireAuth` + the right authz + a bounded Zod validator + `audit()` + `bumpAndRevalidateScores()`. The super-admin cache route (now the first admin write that mutates D1 — it marks `task_scores` stale or, `?hard=true`, deletes score rows) is `isSuperAdmin`-gated and logged; the airscore `/internal/cache/*` endpoints it drives stay off the public route pattern. `bun audit` clean; all 15 overrides held; every prior fix intact, no regressions.

### New findings

#### SEC-29 — Quadratic-time blowup in client-side GPX/KML waypoint-file parsers — **Low** — Open (documented)

- **Files:** `web/engine/src/waypoint-files.ts` — `parseWaypointsGPX` (`content.matchAll(/<wpt\b([^>]*)>([\s\S]*?)<\/wpt>/gi)`) and `parseWaypointsKML` (`/<Placemark\b[^>]*>([\s\S]*?)<\/Placemark>/gi`). Reached from `web/frontend/src/react/comp/CompWaypoints.tsx` (`parseWaypointFile` on a user-selected file, `await file.text()`).
- **Evidence:** the lazy `[\s\S]*?` body match has no matched-close upper bound. A file of many *unclosed* openings — e.g. `"<gpx>" + '<wpt lat="1" lon="2">'.repeat(N)` — makes each opening rescan to end-of-string before failing, giving O(N²) total work. Local timing (reported by the engine subagent): 168 KB → ~1 s, 420 KB → ~6 s, 840 KB → ~24 s; a few-MB file hangs the tab for minutes.
- **Impact:** CPU / event-loop hang in the browser of the user who selects the file — **not** a crash, not cross-user, not server-side. No Worker or Pages Function parses raw waypoint files (the waypoints PUT endpoint accepts already-parsed `WaypointFileRecord[]` JSON via `waypointsBodySchema`, not a raw upload — grep-confirmed). Hence Low: a self-inflicted freeze on one's own machine.
- **Remediation (next round):** bound both loops — bail out after a sane element cap (e.g. `MAX_WAYPOINTS = 5000`, matching the server's) and/or require the matched close within a bounded window; add a unit test with an unclosed-tag payload asserting it returns promptly. A `file.size` pre-check in `CompWaypoints.tsx` before `file.text()` is a cheap second gate.
