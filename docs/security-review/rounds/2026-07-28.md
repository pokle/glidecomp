# 2026-07-28 — Re-review (SSR-seeded identity + server-rendered query strings, static-page account menu, auth-blip retries, dev-router, 3dvis revalidation)

> **17 commits** since the prior round's doc commit (base `e06aa34` → HEAD `7486d12`), ~5.2k insertions across the security-relevant tree. Headline surfaces: (1) **the SSR Pages Function now resolves the visitor** (#492) — a new `AUTH_API` service binding in `functions/comp/[[path]].ts`, the visitor's cookie forwarded to `/api/auth/me`, and the resolved `user` object embedded in `window.__SSR_DATA__`; (2) **the query string is now server-rendered** (#488) — `render(path + url.search, …)` feeds untrusted `?class=`/`?task=` into the React SSR tree; (3) **the static Astro pages grew an account menu** (#479) driven by an inline script and a localStorage hint; (4) **auth resolution retries transient failures** on both the client (`getCurrentUser`) and the worker (`resolveUser`, #481/#484) — a change whose *fail direction* matters; (5) a **new dev-only Worker** (`web/workers/dev-router`, #480) and the container preview (#466); (6) **3dvis bundles gained ETag/304 revalidation** and comp detail now embeds a trimmed route (`taskRouteSummary`). **One new Low (SEC-35, fixed inline this PR); no Critical/High/Medium.** The SSR identity work is well-built: cookie-bearing renders stay `private, no-store`, `serialize()` blocks script breakout, and the seeded user is presentation-only.

### Executive summary

**One new Low, fixed inline; no Critical/High/Medium; every prior fix intact; no new `bun audit` advisory.** The window's riskiest change — embedding the resolved visitor in the server-rendered HTML (#492) — is done right: the user object only appears in cookie-bearing renders, which are always `private, no-store`, the shared `serialize()` blocks `</script>` breakout for the name/email exactly as it does for loader data, and the seeded identity drives chrome only — every authorization decision still happens server-side against the real session. The second riskiest — feeding the raw query string into the SSR render (#488) — was traced end-to-end and never reaches unescaped output: it flows through `StaticRouter` → `useSearchParams()` → React-escaped JSX, while `__SSR_DATA__.path` and the `<head>` builders deliberately keep using the pathname. The new auth retries fail in the right direction everywhere (worker `requireAuth` 503s closed; `optionalAuth` degrades to anonymous on public reads only; 4xx is never retried). The static-page account menu renders its localStorage hint via `textContent` and treats it as a hint, not a credential. The one new finding, **SEC-35 (Low)**, is the 3D-replay bundle route serving `Cache-Control: public` even to signed-in viewers — the same URL 404s for anonymous callers on a hidden `test` comp, so a shared cache holding an admin's copy would serve a test comp's bundle to callers the route itself refuses; the exposure is limited to TLS-terminating shared caches (Cloudflare's edge does not auto-cache Functions-proxied API responses), hence Low. Fixed inline this PR: `bundleHeaders()` now emits `private` for signed-in viewers (mirroring the score route's `cacheControl()` rule) while keeping `max-age` + ETag so the multi-megabyte-bundle 304 saving survives, with a regression test (`visualization-headers.test.ts`).

### New findings

#### SEC-35 — 3D-replay bundle served `Cache-Control: public` to signed-in viewers — **Low** — ~~Open~~ **Fixed (2026-07-28, this PR)**

- **Files:** `web/workers/competition-api/src/routes/visualization.ts` (`bundleHeaders`, both routes).
- **Evidence:** `GET /api/comp/:comp_id/task/:task_id/3dvis` gates hidden `test` comps correctly (404 for anonymous and non-admin callers) but served every 200 with `Cache-Control: public, max-age=300` — and this window's revalidation change (#493) extended that with `stale-while-revalidate=86400` plus an ETag, making the response *more* attractive to shared caches. The response an admin receives for a hidden test comp is therefore declared shared-cacheable: a TLS-terminating shared cache (e.g. a corporate MITM proxy) holding the admin's copy would serve the test comp's replay bundle to other clients for whom the route itself answers 404. Every other gated read surface (scores, field analysis, weather, the SSR pages) already returns `private, no-store` — or `private` — the moment a viewer is signed in, precisely to prevent this class.
- **Impact:** confidentiality of hidden `test`-comp replay bundles (track geometry + pilot names) via shared caches. **Low**: Cloudflare's edge does not auto-cache Functions-proxied API responses, browser caches are per-user, and end-to-end TLS makes honouring shared caches rare (TLS-terminating enterprise proxies being the realistic case). No integrity or authz impact — the route's own gate is correct.
- **Resolution:** `bundleHeaders(cacheKey, signedIn)` now emits `private, max-age=300, stale-while-revalidate=86400` + ETag for any signed-in viewer (mirroring `score.ts`'s `cacheControl()` rule) and keeps `public` for anonymous callers, who can only ever reach non-test comps. `private` rather than `no-store` deliberately: the viewer's own browser may still cache and 304-revalidate the multi-megabyte bundle, so the perf win that motivated #493 is preserved. The sample route stays `public` (resolved with `test = 0` in the query). Regression test: `test/visualization-headers.test.ts`.
