# CLAUDE.md — the GlideComp app

The native iOS and Android app: Expo on React Native, built in the stages of
[docs/2026-10-05-mobile-app-plan.md](../docs/2026-10-05-mobile-app-plan.md),
to the information architecture in
[docs/2026-09-22-ios-app-information-architecture.md](../docs/2026-09-22-ios-app-information-architecture.md).
The root `CLAUDE.md` still applies; this file says how its rules carry over and
what is different here.

## Commands

Run from `mobile/` (or `bun run --cwd mobile <script>`):

| Command | Does |
|---|---|
| `bun run ios` | Build and run on the iOS simulator (`-- --device "iPhone 18 Pro"` to pick one) |
| `bun run android` | Build and run on the Android emulator |
| `bun run start` | Metro only, for a dev build that is already installed |
| `bun run test` | Jest (unit and component) |
| `bun run typecheck` | `tsc` over the app |
| `bun run e2e` | Maestro flows in `.maestro/`, against a booted simulator with the app installed |

From the root, `bun run test:mobile` and `bun run typecheck:mobile` run the
same; both are part of `test:all` / `typecheck:all`, so CI runs them.

Every entry point runs `prepare-sources` first: the engine's scoring
fingerprint, and `scripts/bundle-engine-sample.ts`, which writes the engine
check's sample into `src/engine-check/sample.generated.ts` (gitignored). Call a
tool directly (`bunx jest`, `bunx tsc`) and you skip that — run
`bun run prepare-sources` once first.

`ios/` and `android/` are generated by `expo prebuild` and gitignored
(Continuous Native Generation). Native configuration goes in `app.config.ts`
or a config plugin, never in those folders.

**The Android build needs JDK 17** (`JAVA_HOME`) and `ANDROID_HOME`; see the
plan's stage 0 for the Mac's setup.

### Development and production identities

Every local build is a **development** build: bundle id and package
`com.glidecomp.app.dev`, named "GlideComp Dev", scheme `glidecomp-dev`. Only
`APP_VARIANT=production` (the EAS store profiles) builds `com.glidecomp.app`.
See `app.config.ts` for why: chiefly, a free Apple Personal Team signing a
phone build must never register the store's bundle id. Maestro flows target
`com.glidecomp.app.dev`.

### On your own iPhone

No paid developer account is needed for this; a free Personal Team signs it,
and the build stops opening after 7 days (rebuild to renew).

1. Xcode → Settings → Accounts has your Apple ID (it creates the Personal
   Team), the phone is paired (it appears in DeviceHub), and Developer Mode is
   on (Settings → Privacy & Security on the phone).
2. On the same Wi-Fi as the Mac: `bun run ios -- --device "<phone name>"`.
   It builds, installs, and then keeps Metro running in that terminal; leave
   it open while you use the app. (`--no-bundler` skips starting Metro — use
   it only when `bun run start` is already running elsewhere.) Signing picks
   the Personal Team automatically. The build records the Mac's Wi-Fi
   address, so rebuild if that address changes.
3. The first time only, the launch fails with "profile has not been explicitly
   trusted". On the phone: Settings → General → VPN & Device Management →
   the "Apple Development" developer app → Trust. Then open GlideComp Dev.
4. Allow the local-network prompt; that is how the phone reaches Metro.

A development build loads its JavaScript from Metro over Wi-Fi, so it shows
"No script URL provided" whenever Metro is not running or the phone is on
another network. For a build that runs on its own — on the hill, or for the
airplane-mode checks — add `--configuration Release`: the JavaScript is
embedded and no Mac is needed. (The CLI then sits at "Connecting to …" after
the app has installed and launched; stop it.) A Release build has `__DEV__`
off, so the write guard treats it like a preview build and lets it write to
production. That matters from stage 4, when the app first writes.

### When the simulators misbehave

- **Xcode 27 renamed Simulator.app to DeviceHub**
  (`/Applications/Xcode.app/Contents/Applications/DeviceHub.app`).

- **`expo run:ios` builds and installs, then fails on `osascript ... System
  Events`.** The CLI asks System Events whether the Simulator app is running,
  which needs the terminal to hold macOS Automation permission (System
  Settings → Privacy & Security → Automation). Without it, launch the
  installed build yourself: `xcrun simctl launch <udid> com.glidecomp.app`,
  with Metro running (`bun run start`).
- **Android: "Unable to load script", and Metro never sees a request.** The
  emulator can come up with its Wi-Fi network's routing table missing, so
  nothing — Metro on `10.0.2.2`, or the internet — is reachable ("Network is
  unreachable" from `adb shell toybox nc -z 10.0.2.2 8081`). Turn the emulated
  Wi-Fi off and traffic goes over the emulated cellular link, whose table is
  intact: `adb shell svc wifi disable`.
- **Metro started with `CI=1` does not watch files**, so edits never reach the
  app. Run it without.
- **Android: the first request takes 10 s or more.** The emulator advertises
  IPv6 it cannot route, and Android's HTTP stack waits out a 10 s connect
  timeout before falling back to IPv4. (`ATTEMPT_TIMEOUT_MS` in
  `src/api/client.ts` is longer than that on purpose.) For testing, turn IPv6
  off: `adb root && adb shell sysctl -w net.ipv6.conf.all.disable_ipv6=1`.
- **Testing offline on Android.** A debug build loads its JavaScript from
  Metro, so cutting the network cuts Metro too. Point the build at Metro
  through `adb reverse` instead, which does not use the emulator's network:
  `adb reverse tcp:8081 tcp:8081`, then set the debug host to
  `localhost:8081` (the dev menu's "Change bundle location", or write
  `debug_http_host` into `shared_prefs/com.glidecomp.app.dev_preferences.xml`
  with `run-as`). Then `adb shell svc data disable` cuts only the internet.
  A dev build still takes 10–20 s to start with no network; a release build
  carries its own JavaScript and does not.
- **A typed-routes error for a route you just added** (`'"/me/units"' is not
  assignable…`): the route types are generated by the running Metro. Give it
  a moment and typecheck again.
- **The SDK 58 beta moves fast.** A native crash at launch with
  `Symbol not found … ExpoModulesCore` means one `expo-*` package was
  installed against a newer core than `expo` brings. Move `expo` to the
  latest beta patch and run `bunx expo install --fix`, then rebuild.
  (`expo install --check` asks for Jest 29; `jest-expo` 58 itself requires 30.
  Keep 30.)

## Layout

- `src/app/` — Expo Router routes. `(tabs)/` holds the four tabs; each real
  tab is its own native stack. `submit.tsx` is the Submit sheet and `qr.tsx`
  the full-screen QR, both presented over the tabs from the root stack. **Route shapes are the website's URLs**
  (`/comp/<comp>/task/<task>/route`, `…/weather`), so `compPath()` and
  `taskPath()` from `@glidecomp/client/slug` build the app's own routes, and
  universal links (stage 9) map one to one.
- `src/api/` — the API client, its transport, the queries, the cache, and the
  account's writes (`account.ts`).
- `src/auth/` — signing in and the session: the Better Auth client, the
  cookie transport (`session-fetch.ts`), the identity store (`session.ts`),
  Google and Apple (`providers.ts`). See "Signing in" below.
- `src/ui/` — the grouped list and the query states (loading, error, stale,
  and the report card's own gate, `ReportCardGate`).
- `src/charts/` — the `react-native-svg` charts: the report card's emphasis
  charts, the track data cleaning chart and the weather charts. They draw in
  the screen's own points (`useWidth`), not a scaled viewBox, so their type is
  the platform's real size; colours are the website's tokens (`palette.ts`).
- `src/map/` — the track map and the waypoints map (`@rnmapbox/maps`), the
  only folder that imports the map library.
- `src/lib/` — pure logic behind the screens, unit-tested in `__tests__/`.
- `src/settings/` — what the reader chooses: units (synced to the account
  while signed in, `units-sync.ts`) and appearance (this phone only).
- `src/submit/` — submitting a track (stage 5): the upload queue
  (`queue.ts`), files from outside the app (`incoming.ts`), and the receipt
  the sheet and Me → Track uploads share (`receipt.tsx`). See "Submitting a
  track" below.
- `src/components/` — other shared components, among them
  `SendToInstrument` and `QrCode` (stage 6; see "Sending to an instrument").
- `src/engine-check/` — stage 1's on-device proof that the engine runs (Me →
  Engine check).
- `modules/` — local Expo modules, autolinked. `share-intake` (Android only)
  turns a Share of a file into an open of it.
- `scripts/` — `bundle-engine-sample.ts` (the engine check's sample) and
  `seed-submit-comp.ts` (`bun run seed:submit`: a local comp open today, and
  a forged tracklog that flies it, in `scripts/out/`).
- `.maestro/` — end-to-end flows; `subflows/back.yaml` goes back one screen
  on either platform.

## Shared with the website: `@glidecomp/client`

`web/client` holds what the website and the app share above the engine: the
typed API client (`createApi`), `fetchWithRetry` and the write guard, the wire
types, and the pure slug, time, number, unit, route-wording and weather
helpers. The website's old module paths re-export from it, so its imports did
not change. **Put a pure helper there rather than rewriting it here** — a
pilot should read the same sentence on both.

Stage 3 moved the report card's whole derivation there (`report-card`,
`buildReportCard`; `__tests__/one-derivation.test.ts` fails if either side
grows its own), and the pure halves of every chart and of the map: the
score-curve label placement (`score-curve-layout`), the cleaning chart's frame
and decimation (`track-cleaning`), the weather charts' time axis
(`time-axis`) and wind glyphs (`met`), and the map's features and colours
(`map-geometry`). A platform draws; it does not decide what to draw.

The typed client takes its types from the competition worker's source, so
the app's `tsconfig.json` carries `@cloudflare/workers-types` and `node` for
type-checking only. Responses are cast to the wire types, as on the website.

## Lists and the screens' states

- **Lists are the platforms' own grouped lists** behind `src/ui/grouped-list.tsx`
  (`GroupedList`, `Group`, `Row`, `Note`); screens use those, never `@expo/ui`
  directly. The frame differs by platform (`src/ui/list-shell*.tsx`):
  - **iOS** is `@expo/ui`'s universal `FieldGroup` — a SwiftUI Form — and
    `Group` IS `FieldGroup.Section`.
  - **Android** draws its own Material 3 connected list (Compose `LazyColumn`,
    one card per row). `FieldGroup.Section` wraps every child in a ListItem
    card of its own, and our rows are ListItems, so every row was a card
    inside a card from stage 2 until 2026-10-23. Rows therefore draw no
    background on Android (`ROW_COLORS`); the section paints the card. A row
    that is not a ListItem (`Embedded`, `FieldRow`) is marked `needsInset`
    and gets the ListItem's insets from the section.
  - **Every `Group` is still a direct child of `GroupedList`** — never
    returned from a component of your own. The iOS Form recognises a section
    by its exact component type and wraps anything else in an implicit
    section of its own, and a fragment's second `Group` was once dropped on
    Android (stage 4 lost the Me tab's Profile and Danger zone that way).
    Inline the group, or build it with a plain function you CALL
    (`compGroup({...})` on the Comps tab). Rows inside a `Group` may sit in a
    fragment; both sections open it.
  - Android's list item only styles a **bare string**: text that is wrapped
    (even in a fragment) fails with "Text strings must be rendered within a
    `<Text>`". The `.ios.tsx`/`.tsx` pairs in `src/ui/` return SwiftUI views
    on iOS and plain strings on Android for that reason.
- **Data comes through TanStack Query** (`src/api/queries.ts`), persisted to
  the phone (`expo-sqlite` key-value store), so a comp read this morning
  is there with no signal this afternoon. Queries do not retry on their own:
  `getJson` applies the website's retry rules, with a per-attempt timeout.
- **A chart inside a list is `Embedded`** (`grouped-list.tsx`), which hosts
  React Native views in the native list through `@expo/ui`'s `RNHostView`.
  The report card's section screens are a plain `ScrollView` instead: they
  are mostly charts and arithmetic, not rows.
- **A query can opt out of the phone's cache** with `meta: { persist: false }`
  — the tracklog does, because a megabyte of IGC is a poor use of the space
  that keeps this morning's comps readable this afternoon.
- **Every screen goes through `QueryGate` and `StaleBanner`**
  (`src/ui/QueryStates.tsx`). A failed refresh never replaces data on screen
  (#481); the banner says what is being shown and how old it is, and "not
  found" appears only for a real 404.

## The monorepo, and bun's isolated installs

Bun installs each workspace's dependencies in isolation (`node_modules/.bun`),
pnpm-style. That is what lets the app run React 19.3 (pinned by Expo SDK 58)
while the website stays on its own React. **Do not try to make them share
one copy** — React Native refuses to run unless `react` exactly matches its
renderer.

Three consequences, all already handled; keep them when editing the configs:

- **`@babel/runtime` is a direct dependency** of the app. Babel injects
  imports of it into every compiled file, and nothing hoists it any more.
- **Engine files resolve from `web/engine/`**, which has no `@babel/runtime`.
  `metro.config.js` (`resolver.nodeModulesPaths`) and `jest.config.js`
  (`modulePaths`) both fall back to the app's `node_modules`.
- **Jest's `transformIgnorePatterns` exempts `.bun`**, exactly as jest-expo
  exempts pnpm's `.pnpm`; otherwise nothing in the store is compiled.

## The engine on the phone

`@glidecomp/engine` is imported unchanged. Where it reaches for a platform API
Hermes lacks, the app passes an implementation in rather than changing the
engine:

- `parseXCTaskAsync(content, inflateXctskz)` — Hermes has no
  `DecompressionStream`; `inflateXctskz` uses `fflate`.
- Time zones go through `Intl.DateTimeFormat`, which Hermes supports. Always
  pass the comp's zone (`timezoneForXctsk`), never the phone's.

The engine never changes for the app's sake. If Hermes ever needs an engine
change, it is a scoring change like any other and owes a note in
`web/engine/scoring-changes/`.

## Tests

- **Jest + React Native Testing Library 14.** RNTL 14's `render` is
  asynchronous: `await render(...)`. A component that reads the navigation
  theme needs a `ThemeProvider` around it in the test.
- **Maestro** for journeys, on both simulators. Maestro's `back` is
  Android-only: use `runFlow: subflows/back.yaml`, which swipes on iOS.
  Test ids are distinct prefixes (`comp-row-…`, `task-row-…`): a pattern like
  `comp-.*` also matches the list's own `comp-list` and taps the list, not a
  row. `offline.yaml` runs on Android only (Maestro switches airplane mode
  there), and needs the `adb reverse` set-up above. `results.yaml` walks
  scores → a pilot's series → a report card → a section → the track map.
  `signin.yaml` signs up with an emailed code, names the account, relaunches
  and signs out; it needs a build pointed at the local workers, and reads the
  code from their dev-only `/api/auth/dev-last-otp`
  (`maestro test -e API=http://localhost:8790 .maestro/signin.yaml`). On iOS
  the keychain outlives `clearState`, so a flow must not assume it starts
  signed out.
  `submit.yaml` submits a track from the Submit tab (anonymously on a
  signed-out Android, as the registered pilot on a signed-in iOS) and finds it
  under Me → Track uploads; run `bun run seed:submit` first. Maestro and
  agent-device cannot drive the Android emulator at the same time: close
  agent-device's session before `maestro test`.
- **Better Auth is ES modules only**, some of it `.mjs`; `jest.config.js`
  compiles both (`ESM_ONLY`, and the `.mjs` transform). A test that imports
  anything under `src/api/` pulls it in.
- Flows are data-light: they run against production (read-only) or the
  seeded local workers, whose competitions differ.

## The root rules, as they apply here

| Rule | In the app |
|---|---|
| Australian English; propose UI wording first | Unchanged. Every stage lists its new copy for approval in the PR. Placeholder copy (`StageNote`) is temporary and replaced by the stage named in it. |
| Decisions explainable; the report card's rules (a)–(d) | The engine's explainers, unchanged; GAP parameters from the published `ClassScore.gap_params`; emphasis charts only; the cleaning chart from the downloaded tracklog. |
| Registration is never guessed | The submit sheet resolves through `POST /api/comp/:comp_id/registration/resolve` and asks; `409 identity_ambiguous` means ask again. Names only order the picker. |
| Every submission emails the pilot | The sheet says so up front; the server sends it. |
| Audit log; score staleness | Server-side, so the app inherits them. A new route the app needs follows the same "part of done" rule. |
| A failure to ask is not an answer (#481) | The transport retries transient failures and never records one as "signed out" or "not found". A 4xx is a real answer. |
| A dead link is a searchable one | Universal links use the `${slug}-${id}` shapes; an unresolvable one opens the not-found screen, which uses `GET /api/comp/lookup`. |
| Mobile first; one way to do a thing; a sheet dismisses with Back | Native by construction: system Back and swipe-down dismiss sheets. |
| Altitudes in the reader's unit; radii metric; zero is never missing | The shared `units` module. Waypoint editing stays metric. |
| Never inline geo maths | The engine's `geo.ts` only. |
| Map interaction spec | `@rnmapbox/maps` implements `docs/mapbox-interactions-spec.md`; touch-only differences are written into the spec. |
| Accessibility (WCAG 2.2 AA) | VoiceOver and TalkBack labels, Dynamic Type and font scaling, 44 pt targets, contrast. Audited every stage. |

## Signing in

The same accounts as the website, through the same auth worker; the server's
side is in [docs/auth.md](../docs/auth.md#the-native-app).

- **The session is a cookie kept in the secure store** (Keychain, Android
  Keystore) by `@better-auth/expo`, and attached by `withSession`
  (`src/auth/session-fetch.ts`) to requests for this build's API origin and
  no other, with native `fetch`'s own cookie jar off. Any `Set-Cookie` in a
  response goes back into the store. Never call `fetch` for the API directly:
  `apiFetch` / `api` (`src/api/client.ts`) carry the session and the write
  guard.
- **Who is signed in follows #481** (`src/lib/identity.ts`, the store in
  `src/auth/session.ts`): launch shows the last confirmed user at once, asks
  `/api/auth/me` (and again on returning to the foreground, and when the
  signal comes back), and only a real answer — `{user: null}` or a 401 —
  signs anyone out. A dropped request leaves the reader signed in, and Me says
  it could not check.
- **Signing out, or a real "no", forgets everything cached** (`queryClient
  .clear()`): a comp read as its organiser carries `is_admin`, and a hidden
  comp must not stay readable from the phone. Signing in re-asks every query.
- **Email code** works everywhere. **Google** is offered once the build has
  the app's client ids (`GOOGLE_WEB_CLIENT_ID`, `GOOGLE_IOS_CLIENT_ID`, read
  by `app.config.ts` like the Mapbox token). **Apple** is offered on iOS when
  the signing team has the capability — store builds, or `APPLE_SIGN_IN=1`;
  a free Personal Team cannot have it. Both sign in natively with an ID
  token: the app never signs in through a browser redirect, because that
  would hand the session to a custom-scheme URL another app could claim.
- **A development build reading production cannot sign in**: signing in is a
  write, and `guardWrites` refuses it. Point the build at the local workers
  (`EXPO_PUBLIC_API_ORIGIN`), which also serve the dev-only code lookup the
  sign-in flow uses. A Release build of the development variant signs in to
  production, which is why the auth worker trusts `glidecomp-dev://` there.
- **Role-aware screens**: `is_admin` (comp payload, comps list) shows the
  organiser's rows; `GET /api/comp/pilot/registrations` drives Yours, the
  comp's You group and the task's Your track. Hide, never disable: a row a
  role may not use is absent.

## Submitting a track

The sheet (`src/app/submit.tsx`) follows the website's flow and takes its
rules from `@glidecomp/client/submit` — the endpoint and headers
(`submissionRequest`), the default task, the failure codes and their repairs.
`__tests__/one-derivation.test.ts` fails if either client spells an endpoint
of its own. The server's side is [docs/track-submission.md](../docs/track-submission.md).

- **Written to the phone, then sent.** Submit puts the gzipped track in the
  queue (`src/submit/queue.ts`: an index and one file per track in the app's
  documents directory) and the sheet watches it. Nothing calls a track
  submitted until the server has stored it; until then it is "waiting", and
  Me → Track uploads says so. The decisions — what an answer means, when to
  try again, whose session sends it, what the list keeps — are pure, in
  `src/lib/submission.ts`, and tested.
- **The upload is the one write that bypasses `apiFetch`**, because the
  platform sends it (`File.upload`, a background session on iOS). So the
  queue checks `WRITES_ALLOWED` itself, and attaches the session cookie
  itself — only for a track queued signed in, and only while the same account
  is signed in.
- **Files from outside the app** arrive as a URL: `file://` on iOS (a copy in
  the Inbox, which is deleted once read), `content://` on Android.
  `+native-intent.tsx` parks it (`src/submit/incoming.ts`) and opens the
  sheet. Android's Share (ACTION_SEND) carries its file in an extra React
  Native never reads; `modules/share-intake` rewrites it into a VIEW before
  React Native looks. The document type and intent filters are in
  `app.config.ts`.
- **Trying it locally**: with the workers running, `bun run seed:submit`
  makes a comp open today, forges a tracklog that flies it, and copies that
  onto each booted device — Files → On My iPhone on the iOS simulator,
  Downloads on the Android emulator — for the picker, or for Share → GlideComp
  Dev from the Files app. On the simulator, a new document type only shows in
  the share sheet once LaunchServices has re-read the app: reboot the
  simulator after the first install of a build that adds one.

## Sending to an instrument

One screen, `src/components/SendToInstrument.tsx`, behind three doors: a
task's Route group (`…/task/<task>/send`), the Waypoints screen's Send
button (`…/waypoints/send`) and a task in My flights' library
(`/flights/task/<code>`). What it offers and what each file holds come from
`@glidecomp/client/instrument`, over the engine's exporters, so a file from
the phone is the file the website's worker serves, name and all.

- **Written on the phone, then shared** (`src/lib/send-file.ts`): no request,
  so it works offline once the task has been read. iOS chooses the apps a
  share sheet offers by type: GPX and KML go as their own types, the rest as
  `public.data`, and the receiving app goes by the extension.
- **The QR is `/qr`, a full-screen modal**, black on white in either theme,
  kept awake while it is up. It takes the source's ids as route parameters
  (`comp`, `task`, `code`, `swap`) and reads the task from the cache rather
  than carrying a 3 KB payload through the router.

## The organiser (stage 7)

Every organiser screen writes through `src/api/organiser.ts`: one function
per existing competition-api route, each refetching what it can have changed
(`refreshComp`). A refusal comes back as a `WriteError` carrying the server's
own sentence; screens show it through `useFormSave` (`src/ui/use-form-save.ts`),
which also holds the unsaved-changes guard and the destructive confirm.
Nothing here audits or bumps scores itself: the server does both for every
route the app calls, which is why the app adds no route of its own except
the organiser's notes (migration 0037, through the comp PATCH).

- **Hide, never disable**: every organiser row is behind `is_admin`.
- **The logic is the website's** (see "Shared with the website"): the route
  editor's rows and assembly, the roster CSV and CIVL fill, Check altitudes'
  verdicts and the terrain decoder, the scoring form. If a rule needs
  changing, change it in `@glidecomp/client` so both clients move together.
- **Forms are React Native** (`src/ui/form.tsx`: `Field`, `Choices`,
  `Toggle`, `DangerButton`), not the native grouped list: they are typed
  into, and the list's rows are not inputs. A sheet over a form (the route
  editor's turnpoint) is an RN `Modal` with `presentationStyle="pageSheet"`.
- **Units**: altitudes typed in the reader's unit (`toAltitudeInput` /
  `fromAltitudeInput`), radii always metres; Check altitudes is metric, as the
  waypoint file is. Gate and deadline times are typed in the comp's zone and
  stored as UTC.

## The track map

`@rnmapbox/maps` draws the report card's map, following
`docs/mapbox-interactions-spec.md` (its "Native app" section lists what a
touch screen does differently). Two tokens, neither committed:

- **The public token** (`pk.…`) is `REACT_NATIVE_MAPBOX_PUBLIC_TOKEN`, read by
  `app.config.ts` from the environment or the repository's root `.env` (the
  file the website's `VITE_MAPBOX_TOKEN` lives in; a worktree has its own
  copy, so add the line there too). It ends up in `extra.mapboxPublicToken`;
  a public token ships inside every app by design. A build without it shows a
  sentence where the map would be, rather than crashing.
- **The secret download token** (`sk.…`, `DOWNLOADS:READ`) lives only in
  `~/.netrc` (`machine api.mapbox.com login mapbox password sk.…`, mode 600),
  where CocoaPods reads it for the Mapbox SDK. Android's Maven repository no
  longer needs it.

A new native module means regenerating the native projects:
`bunx expo prebuild --clean`, then `pod install` in `ios/`.

## Which API a build talks to

There is no staging environment. `EXPO_PUBLIC_API_ORIGIN` picks the origin
(read when Metro bundles, so restart Metro after changing it); unset, it is
`https://glidecomp.com`. A development build reads production but **never
writes to it**: `guardWrites` in `@glidecomp/client/transport` refuses
anything that is not a read before it leaves the phone. Point a build at the
local workers (`bun run dev:workers` on `:8790`; the Android emulator reaches
them as `10.0.2.2`) and it may write, since that data is the developer's own.
Preview, beta and store builds write to production. Me → This build says
which API a build reads.
